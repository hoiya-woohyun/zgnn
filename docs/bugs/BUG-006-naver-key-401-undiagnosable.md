# BUG-006 — 네이버 검색 키가 401 인데, 왜 401 인지 알 방법이 없다

> 최종 수정: 2026-09-28 (v5: **진짜 원인 — 네이버 검색 API 가 두 개인데 우리가 틀린 쪽에 대고 있었다.** 사용자 키는 NAVER API HUB 것이고 코드는 개발자센터 규격이었다.
> 호스트·경로·헤더를 전부 옮겼다(`lib/naverSearchApi.mjs`). 값은 처음부터 멀쩡했다 — trim 도 마스킹도 이 버그의 원인이 아니라 **원인을 못 보게 했던 것들**이었다)
> 이전 (v4: **숨김 입력을 `*` 마스킹으로 바꿨다** — 이 버그를 어렵게 만든 조건(붙여넣기가 들어갔는지 알 수 없음)을 원인 쪽에서 없앤다.
> `data:login` 의 비밀번호도 같은 함수라 함께 바뀐다. 내주는 것은 자릿수 하나)
> 이전 (v3: **401 의 세 갈래를 실측으로 갈랐다** — 빈 값·헤더 누락은 `Not Exist …`, 둘 다 갔는데 거부면 `(1000)`. 그래서 `1000` 은
> "값은 갔는데 조합을 모른다" 로 **좁게** 읽어야 한다. 남은 갈래를 가를 `describeKeyShape`(길이·글자 종류만, 값은 아님) 추가. 사용자 2차 실행에서 `1000` 확인)
> 이전 (v2: **실측이 라벨 설계를 뒤집었다** — 실제 401 본문은 "Not Exist Client ID" 가 아니라 `NID AUTH Result Invalid (1000)` 이고, 갈래를 정하는 것은 **괄호 숫자**다)
> 이전 (v1: 신설 — 첫 `pnpm data:collect` 가 401 로 멈췄고, 원인을 좁힐 근거가 로그에 없었다)
> 상태: 진단 도구 완료. **공백은 원인이 아니었다**(trim 뒤에도 `1000`). 남은 갈래는 값 자체 · 뒤바꿔 입력 · 개발자센터 키가 아님 — 3차 실행의 「모양」 줄이 가른다.

## 진짜 원인 (v5) — **네이버 검색 API 는 두 개다**

사용자가 NCP 문서 링크(`guide.ncloud-docs.com/docs/apihub-application`)를 보내면서 드러났다.
키는 **NAVER API HUB(NCP)** 에서 발급받은 것이었고, 코드는 **개발자센터**(`openapi.naver.com`) 규격이었다.

| | 개발자센터 (코드가 대고 있던 곳) | NAVER API HUB (사용자 키의 출처) |
|---|---|---|
| 호스트 | `openapi.naver.com` | `naverapihub.apigw.ntruss.com` |
| 경로 | `/v1/search/blog.json` · `/v1/search/local.json` | `/search/v1/blog` · `/search/v1/local` |
| 헤더 | `X-Naver-Client-Id` · `X-Naver-Client-Secret` | `X-NCP-APIGW-API-KEY-ID` · `X-NCP-APIGW-API-KEY` |
| 신규 발급 | **2026-07-31 종료** | 여기만 가능 · **한시적 무료** |

**왜 아무도 못 알아챘나 — 두 시스템이 자격증명을 똑같이 "Client ID / Client Secret" 이라고 부른다.**
API HUB 콘솔도 그 이름으로 보여 준다(`Client ID (X-NCP-APIGW-API-KEY-ID)`). 그래서 값을 손에 쥐고도
어느 쪽 것인지 구별할 단서가 없고, 틀린 쪽에 보내면 그냥 401 이다. 값은 **처음부터 멀쩡했다.**

**파라미터와 응답 필드는 두 시스템이 같다**(query·display·start·sort / title·link·description·bloggername·postdate / mapx·mapy).
그래서 옮기면서 `collect/naverBlog.mjs` 의 파싱과 `naverLocal.mjs` 의 좌표·주소 해석은 한 줄도 안 건드렸다 —
바뀐 것은 **어디로 무엇을 들고 가는가** 뿐이다(`scripts/lib/naverSearchApi.mjs` 가 정본).

### 앞선 v1~v4 는 헛수고였나 — 아니다, 다만 원인이 아니었다

trim(v1~v2)·`*` 마스킹(v4)·`describeKeyShape` 는 **이 버그의 원인이 아니라 원인을 못 보게 하던 것들**이었다.
셋이 없었다면 v5 에 도달하기까지 더 걸렸을 것이다 — 특히 "값은 둘 다 갔는데 조합을 거부당했다"(내부코드 `1000`)를
가른 덕에 입력 경로를 파는 것을 멈추고 **키의 출처**를 의심할 수 있었다. 진단 장치는 남긴다.

한 가지는 v5 에서 **물러섰다**: `describeKeyShape` 의 "Secret 이 ID 보다 길면 뒤바뀐 것" 단정은
개발자센터 키를 전제한 것이었다. API HUB 키의 자릿수는 실측이 없어 단정을 걷고 두 길이를 나란히 보여 주기만 한다.

### 옮긴 뒤에도 열린 것

- **실제 통과는 아직 못 봤다.** 진짜 키가 있어야 확인된다. 475 테스트·lint 통과와 게이트웨이 실측(아래)은
  "규격에 맞췄다" 까지이고 **엔드투엔드 성공이 아니다.**
- 게이트웨이 실측(2026-09-28, 자격증명 없이): `/search/v1/blog`·`/search/v1/local` → **401**(경로 있음),
  없는 경로 → **404**. 오류 모양은 `{"error":{"errorCode":"200"|"300", …}}` 로 **감싸져 있고**,
  개발자센터의 평평한 `{errorMessage, errorCode}` 와 **번호 공간이 겹친다**(`200`/`300` vs `024`) → 모양으로 갈라야 한다.
- **⚠️1(좌표 포맷)은 여전히 안 풀렸다.** API HUB 의 지역 검색 문서도 `mapx`/`mapy` 를 "WGS84 좌표계 기준" 이라고만 쓰고
  예제 값이 `{경도}`·`{위도}` 자리표시자라 정수/소수를 확정할 수 없다. `parseNaverCoord` 의 제주-범위 검사가 그대로 방어선이다.

## 증상

키를 발급받아 처음 `pnpm data:collect` 를 돌리면 숨김 입력 두 번을 받은 직후 첫 요청에서 죽는다.

```
NAVER_CLIENT_ID(숨김 입력):
NAVER_CLIENT_SECRET(숨김 입력):
Error: 네이버 검색 API 실패: status=401 query=제주 강아지 동반 카페
```

`pnpm data:login` 세션은 정상이다(세션 검사가 키 입력보다 **먼저**라, 프롬프트가 떴다는 것 자체가 세션이 살아 있다는 증거다).

## 무엇이 진짜 문제인가 — 401 이 아니라 **401 을 가를 수 없다는 것**

401 을 낼 수 있는 원인이 최소 셋인데 **셋이 구별되지 않았다.**

| 원인 | 어디서 고치나 |
|---|---|
| 값이 틀렸다 — 오타 · **붙여넣기가 끌고 온 앞뒤 공백** · ID/Secret 순서 바꿔 입력 | 다시 입력 |
| 애플리케이션에 「검색」이 사용 API 로 없다 | 개발자센터 → 애플리케이션 → 사용 API |
| 다른 네이버 계정의 애플리케이션을 보고 있다 | 계정 전환 |

가릴 근거가 둘 다 막혀 있었다.

1. **로그 위생이 진단까지 막았다.** [05-security](../todo/05-security.md) 의 "`fetch` 에러 메시지에는 status·query 만" 은
   키와 **검색 결과**(약관상 복제·저장 금지)가 로그에 남지 않게 하려는 규칙인데, 실패 응답까지 싸잡아 버려 원인이 사라졌다.
2. **`errorCode` 를 찍었어도 안 갈렸다.** 인증 실패는 전부 `024` 다. 갈리는 것은 `errorMessage` 뿐이다.

### 실측이 설계를 한 번 뒤집었다

처음 고칠 때는 문서·블로그에서 흔히 인용되는 문구("Not Exist Client ID" · "Not Exist Client ID/Secret")로 갈래를 나눴다.
**가짜 키로 실제 호출해 보니 그렇게 오지 않았다**(2026-09-28):

```
status 401 {"errorMessage":"NID AUTH Result Invalid (1000) : Authentication failed. (인증에 실패했습니다.)","errorCode":"024"}
```

갈래를 정하는 것은 문구가 아니라 **괄호 안의 숫자**(`1000`)다. 문구 매칭만 있었으면 라벨이 하나도 안 붙어
"고쳤는데 여전히 아무것도 안 갈리는" 상태로 배포될 뻔했다. 테스트가 통과한다는 것과 동작한다는 것이 다른,
이 레포에서 여러 번 반복된 자리다(옛 OSM/CARTO 의 `statuses`, 타일 호스트, `.d.ts` 의 `Position`).
그래서 `naverApiError.mjs` 는 숫자를 뽑는 것을 본령으로 삼고 문구 매칭은 보조로 남겼으며,
`naverApiError.test.mjs` 는 **실측 본문 그대로**를 못 박는다.

### 401 은 세 갈래다 — 그래서 `1000` 은 좁게 읽어야 한다

가짜 헤더로 직접 호출해 갈래를 실측했다(2026-09-28). 전부 `status=401 errorCode=024` 인데 문구가 다르다.

| 보낸 것 | `errorMessage` |
|---|---|
| 헤더 없음 · 빈 문자열 | `Not Exist Client ID` |
| ID 만 있고 Secret 없음 | `Not Exist Client Secret` |
| **둘 다 값이 있으나 인증 거부** | **`NID AUTH Result Invalid (1000)`** |

→ `1000` 은 **"두 값 모두 전달됐는데 네이버가 그 조합을 모른다"** 다. 값이 비어서 안 갔거나 헤더가 빠진 경우는
애초에 다른 문구로 오므로 **이 갈래에서 제외된다.** 이 구분이 없으면 1000 을 "값이 안 갔나?" 로 넓게 읽어 엉뚱한 데를 판다.

### 2차 실행 결과 — 공백은 원인이 아니었다

trim 을 넣은 뒤 사용자가 다시 돌렸는데 여전히 `(1000)` 이었다. 위 표에 따라 **빈 값·공백 누락은 배제**되고,
아래 「보이지 않는 공백」은 가능성으로만 남는다(원인이 아니라 **이 버그를 찾기 어렵게 만든 조건**이었다).

남은 갈래 셋을 가르려면 **우리가 무엇을 보냈는지**를 알아야 하는데, 숨김 입력이라 그걸 볼 방법이 없었다.
그래서 401 일 때만 **값의 모양**(길이·글자 종류, 값 자체는 아님)을 찍는 `describeKeyShape` 를 넣었다.
개발자센터는 Client ID 가 Secret 보다 길므로, **Secret 이 더 길면 둘을 뒤바꿔 입력한 것**이다 —
숨김 프롬프트를 연달아 두 번 받는 흐름에서 가장 흔한 실수이고, 지금까지 눈으로 잡을 방법이 전혀 없었다.

## 찾기 어렵게 만든 조건 — 보이지 않는 공백

`scripts/lib/readHidden.mjs` 의 리듀서는 `c >= 0x20` 인 글자를 그대로 쌓는다. **0x20 이 공백 그 자체다.**
그리고 호출부에 `trim` 이 없었다. 즉 복사할 때 딸려 온 앞뒤 공백 한 칸이 값에 그대로 들어간다.

**이 실수만 유독 잡기 어려운 이유는 숨김 입력이기 때문이었다.** 화면에 아무것도 안 찍히므로 사용자가 눈으로 확인할 방법이 없고,
돌아오는 신호는 401 하나뿐이라 "값이 문제" 라는 것조차 알 수 없다. 보통의 비밀번호 입력이라면 한 번 더 쳐 보고 끝날 일이
여기서는 **애플리케이션 설정을 의심하며 개발자센터를 뒤지는 쪽으로** 사람을 보낸다.

### 그래서 조건 자체를 없앴다 — `*` 마스킹 (v4)

`readHidden` 이 글자 수만큼 `*` 를 찍는다. 붙여넣기가 **들어갔는지**와 **몇 글자인지**가 그 자리에서 보이므로,
잘림·중복·아예 안 들어감이 401 을 기다리지 않고 잡힌다. 지우기는 `\b \b` 로 되돌린다.

- **함께 바뀌는 것**: `pnpm data:login` 의 비밀번호도 같은 함수를 쓴다. 두 소유자를 가진 함수라 한쪽만 바꿀 수 없고,
  "붙여넣었는데 들어갔나" 는 비밀번호에도 똑같이 필요한 신호라 그대로 둔다.
- **내주는 것**: 자릿수 하나. 어깨너머로 보는 사람에게 길이가 노출된다. 값·글자는 여전히 안 나가고,
  이 앱의 위협 모델(에이전트가 값을 읽는 것 · 파일에 남는 것)과는 무관하다. `sudo` 처럼 완전 무표시를 택하지 않은 이유는
  여기 입력이 **외워 치는 비밀번호가 아니라 붙여넣는 난수**여서다 — 무표시의 이득(길이 은닉)보다 손해(붙여넣기를 검증할 수 없음)가 크다.
- **거짓말하지 않게 못 박은 것**: 방향키·Alt 시퀀스는 버려지므로 `*` 가 늘지 않아야 한다(늘면 사용자가 "들어갔다" 고 잘못 읽는다).
  한글·이모지는 코드포인트 하나에 `*` 하나. 둘 다 테스트에 있다.

## 수정

1. **소유자 쪽에서 턴다.** `collect-blog.mjs` 가 env 와 숨김 입력 결과를 모두 `trim` 한다.
   `readHidden` **안에서** 털지 않는다 — `data:login` 의 비밀번호와 공유하는 함수이고, 비밀번호는 앞뒤 공백이 값일 수 있다.
   네이버 키는 그럴 수 없으므로 판단이 갈리는 자리를 소유자에게 둔다.
2. **`analyze-candidates.mjs` 의 env 도 턴다.** 이쪽은 숨김 입력이 없어 `export NAVER_CLIENT_ID=' xxx '` 한 줄이 그대로 401 이 되는데,
   분석은 글마다 몇 분씩 도는 일이라 **중간에** 터진다(수집처럼 첫 요청에서 바로 알려 주지 않는다).
3. **실패 응답에서 `errorCode` 와 내부코드·라벨만 꺼낸다** — `scripts/lib/naverApiError.mjs`(+ 7 테스트).
   내보내는 글자는 `errorCode`·`\d+` 로 뽑은 내부코드·이 레포의 상수 라벨뿐이고, **`errorMessage` 원문은 어떤 경우에도 안 나간다**.
   모르는 내부코드는 뜻을 지어내지 않고 번호와 "아직 뜻을 모른다" 를 함께 보여 준다 — 다음 사람이 `AUTH_SUBCODES` 에 한 줄 더할 단서다.

메시지가 이렇게 바뀐다:

```
네이버 검색 API 실패: status=401 errorCode=024 (이 Client ID 로 인증이 안 된다 — 값이 틀렸거나(공백 포함) 다른 네이버 계정의 애플리케이션이다) query=제주 강아지 동반 카페
```

위 줄은 가짜 키로 **실제 API 를 불러 받은 출력**이다(추정이 아니다).

## 남은 것

- [ ] **사용자 재실행으로 실제 원인 확정.** 내부코드가 `1000` 이면 값·계정 쪽이고(공백은 이제 trim 이 막으므로, 그래도 1000 이면 값 자체나 계정이다),
      **모르는 번호가 나오면 그 번호가 새 단서다** — `AUTH_SUBCODES` 에 뜻을 적어 넣는다. `사용 API` 라벨이면 개발자센터 설정이다.
- [ ] 두 번째 사례(올바른 ID + 틀린 Secret)의 내부코드를 아직 모른다 — 실제 키가 생겨야 확인된다.
- [ ] 3차 실행의 「보낸 값의 모양」 줄로 갈래 확정: Secret 이 더 길면 **뒤바꿔 입력**, 길이가 개발자센터 키와 안 맞으면
