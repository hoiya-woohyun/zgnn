# BUG-017 — 검수 대기 후보를 1000건까지만 읽어 넘친 가게가 묶이지 않는다

> 최종 수정: 2026-10-11 (v2: 블로그 이력 조회도 같은 모양 — 덩어리 + 페이지로)
> 이전 2026-10-11 (v1: 신설 — 빠르게 돌리려 `--limit 300` 을 준 날, 시작 줄의 `pending 후보 1000건` 이 실제 1,075건의 잘린 값이었다)
> 상태: 고침(`selectAllPages` — 분석·coverage). `/admin` 의 후보 조회는 아직 안 봤다.

## 증상

`pnpm data analyze` 시작 줄이 두 실행 연속 `pending 후보 1000건` 이었다. 그 사이 첫 실행이 신규 후보 12건을 넣었는데 숫자가 그대로였다.
원격에서 세면 `status='pending'` 은 **1,075건**. 에러도 경고도 없다.

## 원인

`analyze-candidates.mjs` 가 이전 실행의 pending 후보를 `.limit(1000)` 으로 읽었다. PostgREST 는 한 번에 최대 1000행을 주고 **넘친 행을 에러 없이 자른다** —
`.limit(1000)` 은 상한을 적은 것이 아니라 상한과 같은 숫자를 한 번 더 적은 것이라 아무것도 막지 않았다. 코드 곳곳의 "늘어나면 range() 로 페이지네이션"
주석은 그때가 오면 누군가 알아챌 것을 전제했지만, 잘린 결과는 정상 결과와 모양이 같다.

이 목록은 두 가지의 씨앗이다 — 같은 가게가 또 나오면 먼저 난 후보에 묶는 `dupOf`(`newNamesSeen`·`newPlacesSeen`), 사람이 고친 후보를 다시 만들지 않는
`editedKeysFor`. 빠진 75건(정렬 없이 잘려 어느 것인지도 매번 다르다)의 가게를 다룬 새 글은 묶이지 않고 **검수 대기에 쌍둥이**를 만든다.
게시된 `places` 에는 닿지 않지만, 분석을 빨리 많이 돌릴수록 pending 이 늘어 빠지는 몫도 커진다. 빌드·테스트는 전부 초록이다.

`pnpm data coverage` 의 칸별 검수 대기 수도 같은 질의라 같은 만큼 덜 셌다.

## 수정

- `scripts/lib/selectAllPages.mjs` — 정렬 키(`order('id')`)로 순서를 고정하고 `range()` 로 **빈 페이지가 나올 때까지** 넘긴다. 다음 페이지는 받은 행 수만큼
  앞에서 시작해, 서버 상한이 페이지 크기보다 작아도 건너뛰거나 덜 찬 페이지를 끝으로 읽지 않는다(요청 한 번 더가 비용의 전부).
- 분석의 pending 조회와 `data-coverage.mjs` 의 대기 조회가 이것을 쓴다.
- 같은 실행 시작부의 **블로그 이력 조회**(`noteSinglePlaceBlogs` — 이번 후보 글 블로그들의 분석 끝난 글)도 같은 모양이었다(코드 리뷰 지적). `--limit 300` 이면
  후보 글 820건의 블로그 이력이 1000행을 넘을 수 있고, 잘리면 업주 블로그(`singlePlaceBlogs`)를 못 알아봐 그 글이 앞줄에 선다 — 후보가 틀리지는 않고 순서만.
  블로그 id 를 `chunkForUrlFilter` 로 자르고 덩어리마다 `selectAllPages`(`order('url')` — 기본 키) 로 읽는다.

## 남은 것

- `/admin`(`src/lib/admin*.ts`)이 검수 대기 후보를 어떻게 읽는지 확인하지 않았다 — 같은 모양이면 운영자 화면에서 75건이 안 보인다.
- `--limit` 을 500 이상 주면 나머지 글 창(`.limit(postWindow + 집중 글 수)`)이 1000을 넘어 같은 식으로 잘린다 — 순서·개수만 줄어드는 쪽이라 지금은 실행당 300 으로 둔다.
- 이미 생긴 쌍둥이(잘린 동안 들어간 신규 후보)는 따로 고치지 않았다 — 검수 화면에서 같은 이름 묶음이 둘로 보이면 이것이다.
