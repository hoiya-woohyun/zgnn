# 홈 상단을 헤더 UI 로 — 맨 위 면을 전 화면 크림으로 통일

> 최종 수정: 2026-09-29 (v4: 종류 카드 숫자 기준 — "가능 N · 확인 M", 목록 머리와 같은 `countByLevel`)
> 이전 (v3: 구현 완료. 실기기 실험 두 가지는 "착수 전" 이 아니라 **확인**으로 남는다 — 설계가 두 후보 모두에서 같은 답을 내게 바뀌었기 때문)
> 이전 (v2: 크림 띠의 원인 후보를 찾았다 — 축약 줄이 샘플링을 가로챈다. 헤더는 불투명이어야 한다는 제약, 착수 전 실기기 실험 둘)
> 이전 (v1: 신설)
> 상태: **채택 · 구현됨.** 결정은 [ADR-010 v3](../decisions/ADR-010-shell-owned-safe-area.md) 이 정본이고,
> 이 문서는 그 실행 계획과 남은 실기기 확인 목록이다.

## 왜 하는가

지금 **홈만 맨 위 면이 어둡다**(현무암 히어로, `--color-ink`). 다른 화면은 전부 페이지
바탕(크림)이라 아무것도 안 해도 맞는데, 이 예외 하나가 두 곳에서 비용을 만든다.

1. **브라우저가 칠하는 띠와 어긋난다.** 주소창을 아래에 둔 iOS Safari 탭에서는
   `safe-area-inset-top` 이 **0** 이다 — 상태바 자리가 우리 레이아웃 뷰포트 밖이라 CSS 로
   손이 닿지 않고, 그 띠는 Safari 가 직접 칠한다. 그래서 잉크 히어로 위에 크림 띠가 남았다.
   지금은 셸이 `<html>` 배경을 화면 맨 위 블록의 색으로 맞춰 우회하고 있다
   (→ [ADR-010 v2](../decisions/ADR-010-shell-owned-safe-area.md) "브라우저가 칠하는 띠").

   **그런데 그 우회가 실제로 동작하는지 의심스럽다.** `collapsingTitleBar.tsx` 의 축약 줄은
   `fixed inset-x-0 top-0` + `bg-secondary/95`(크림)이고, 접히지 않은 동안 사라지는 것이 아니라
   **`opacity-0` 으로 남아 있다.** Safari 26 의 샘플링이 opacity 까지 본다는 보장이 없으므로,
   잉크 히어로가 맨 위에 있는데도 Safari 가 이 보이지 않는 줄에서 크림을 가져갔을 수 있다 —
   2026-09-17 사진의 모습이 정확히 그것이다. 사실이라면 `<html>` 배경 동기화는 **처음부터 이
   줄에 가려 무력했다**. 4단계에서 지울 때 잃을 것이 없다는 뜻이고, 목표 상태(전 화면 크림)
   에서는 같은 줄이 **맞는 색**을 주므로 오히려 이로워진다.

   **구현은 이 질문을 실험으로 가르지 않고 없앴다.** 축약 줄을 불투명 `bg-secondary`(크림)로
   바꿨고 맨 위 면도 전부 크림이라, Safari 가 그 줄을 샘플링하든 `body` 를 샘플링하든 답이
   같다. 어느 쪽이 사실이었는지는 이제 화면에 영향을 주지 않는다.
2. **PWA 상태바 글씨 색을 앱 전체가 하나 골라야 한다.** `layout.tsx` 의
   `appleWebApp.statusBarStyle: 'black-translucent'` 은 화면마다 바꿀 수 없는 값이다. 이 값이
   최신 iOS 에서 글씨를 흰색으로 고정하는지 시스템 외형을 따르는지는 **아직 확인하지 않았다**
   (5단계와 같은 이유로 단정하지 않는다). 흰색 고정이라면 홈(잉크)에서는 맞고 크림 화면에서는
   읽히지 않는다.

   확실한 것은 따로 있다 — **지금은 화면마다 맨 위 면 색이 달라, 어떤 값을 골라도 절반은
   틀린다.** 전 화면을 한 색으로 모으는 것이 이 문제를 비로소 *해결 가능하게* 만든다.
   구현은 `default`(검정 글씨)를 골랐고, **그 값이 실제로 어떻게 보이는지는 아래 "실기기"
   목록에 남는다** — 데스크톱에서는 판별 불가능하다.

**맨 위 면을 전 화면 크림으로 통일하면 둘 다 동시에 사라진다.** 우회 장치도 지운다.

## 목표 상태

```
┌───────────────────┐
│ 3:53    ◂▸ ▬▬ ■   │  ◀ Safari/상태바 띠 = 크림 (전 화면 동일)
├───────────────────┤
│                   │  ◀ 크림 여백
│  ╭─────────────╮  │
│  │ 🐾           │  │
│  │ 강아지랑 제주 │  │  ◀ 잉크 히어로 (라운드 판으로 내려온다)
│  │ 숙소 식당 카페│  │
│  ╰─────────────╯  │
│   ┌───────────┐   │
│   │ 짱구누나 … │   │
```

현무암 잉크 자체는 **버리지 않는다**([ADR-003](../decisions/ADR-003-untitled-ui-and-palette.md)
팔레트 유지). 포기하는 것은 "히어로가 화면 끝까지 깔린다" 는 어법 하나뿐이고, 라운드 판으로
띄우는 것이 그 절충안이다. 팔레트를 안 건드리므로 `pnpm icons` 재생성은 **불필요**하다.

## 범위 결정 — 상세(`/place/:id`)를 포함할 것

홈만 고치면 `/place/:id` 는 맨 위 면이 **종류 색 그라디언트**라 여전히 크림이 아니다. 그러면
`appShell` 의 `<html>` 배경 동기화 `useEffect` 가 **상세 하나 때문에** 남는다.

상세도 앱바 밑에서 시작하게 하면(제목 판 위에 크림 띠) 전 화면이 통일되고 **그 장치를 통째로
지울 수 있다.** 코드가 가장 적게 남는 쪽이므로 이 범위를 권한다. 상세를 빼기로 하면 아래
3단계만 건너뛰고, 4단계의 `useEffect` 삭제도 하지 않는다(홈 관련 분기만 빠진다).

## 구현 결과 (2026-09-17)

아래 6단계를 계획대로 진행했고, 계획과 갈린 곳만 적는다.

- **1단계** — 히어로를 `px-4 pt-6 md:px-6 md:pt-10` + `rounded-2xl p-6` 라운드 판으로. 시작
  높이를 `PageHeader` 와 같은 값으로 맞춰, 홈도 다른 루트 화면과 첫 블록이 같은 자리에서
  시작한다. **인사 카드의 `-mt-10` 은 버렸다** — 카드가 히어로와 같은 폭이라 겹치면 판의
  아래 모서리를 통째로 덮어 판으로 보이지 않는다. 그 겹침에 자리를 내주던 `pb-16` 도 함께.
- **2단계** — 새로 만들지 않았다. 홈은 이미 `CollapsingTitleBar` 를 쓰고 있었다. 대신 v2 가
  찾아낸 제약을 반영해 **배경을 불투명 `bg-secondary` 로** 바꿨다(`bg-secondary/95` +
  `backdrop-blur` → 제거). 히어로가 `px-4 md:px-6` 로 들어오면서 축약 줄의 제목과 큰 제목의
  좌우 위치도 저절로 맞았다.
- **3단계** — **계획이 자기모순이었다.** 적어 둔 클래스(`-mt-14 pt-14`)는 판이 앱바 줄을
  *덮는다*는 뜻인데, 같은 단계의 목표 문장("앱바 밑에서 시작", "앱바 줄 높이만큼 크림이
  남는다")과 범위 결정 절("제목 판 위에 크림 띠")은 그 반대를 말한다. **아무것도 안 붙이는
  쪽으로 갔다** — 음수 마진을 통째로 버려 판이 앱바 줄 아래에서 시작한다. 근거: (1) 이 문서의
  논지가 "맨 위 면을 전 화면 크림" 인데, `-mt-14 pt-14` 면 브라우저 탭(인셋 0)에서 문서 첫
  픽셀이 종류 색이라 논지가 환경을 가린다. (2) `/saved`·`/dog` 등 다른 하위 화면은 **원래부터**
  앱바 줄이 크림 위에 있었다 — 상세만 예외였던 것이 규칙으로 들어온다. (3) 덤으로 앱바를
  `fixed` 로 못 바꾸던 결합(그 이유가 이 음수 마진이었다)이 풀린다.
- **4단계** — 계획대로. `data-top-surface` · `@utility under-app-bar` · `<html>` 배경 동기화
  `useEffect` 가 코드에서 사라졌다(`grep` 0건).
- **5단계** — `statusBarStyle: 'default'`, `themeColor`·`manifest.theme_color` 모두 `#faf8f4`.
  `default` 와 `viewport-fit: cover` 의 상호작용은 **단정하지 않고 주석과 아래 목록에 남겼다.**
  레이아웃이 안 깨지는 것까지만 단언한다 — 내용이 상태바 밑까지 깔리면 셸의 인셋 여백(크림)이
  그 자리를 쓰고, 안 깔리면 인셋이 0 이 되어 여백만 사라진다. **띠가 크림으로 칠해질지
  시스템 흰색이 될지는 아래 실기기 목록으로 넘긴다.**
- **6단계** — `bleed-top-*` · `top-safe` 유지. 남은 사용처는 둘러보기 검색 줄 하나다.

**검증하며 알게 된 것** — 빌드 CSS 에는 `bleed-top-10` 선언이 아직 생성된다. 코드에 사용처가
없는데도 남는 이유는 Tailwind v4 의 자동 소스 탐지가 **`docs/` 의 코드 예시까지 스캔**하기
때문이다(이 문서의 "현재:" 블록이 그것이다). 아래 검증 5번을 쓸 때 이 점을 감안할 것 —
빌드 CSS 에 클래스가 보인다고 코드가 그것을 쓰는 것은 아니다.

## 단계

순서가 중요하다. **의존성 먼저, 사용 나중** — 중간 저장 상태에서 HMR 에러가 나지 않게 한다.

### 1. 홈 히어로를 라운드 판으로 내린다

`src/screens/homePage.tsx` — 현재:

```tsx
<header data-top-surface className="basalt bleed-top-10 px-4 pb-16 text-white md:px-6">
```

- `data-top-surface` **삭제**(4단계에서 읽는 쪽이 사라진다).
- `bleed-top-10` **삭제** — 더 이상 맨 위 블록이 아니라 위로 번질 이유가 없다.
- 위에 크림 여백을 두고 라운드 판으로 만든다. 좌우 여백은 다른 화면의 `px-4 md:px-6` 계약에
  맞춘다 — 지금 히어로만 셸의 중앙 정렬 폭을 넘어 끝까지 깔리는 예외였는데, 그 예외가 없어진다.
- 히어로 아래 인사 카드의 `-mt-10`(겹쳐 올리는 음수 마진)이 라운드 판과 어떻게 만날지 함께 본다.

### 2. 헤더 UI 를 무엇으로 할지 정한다

`src/components/layout/collapsingTitleBar.tsx` 가 이미 있다(준비물 화면이 쓴다). 제목이 화면
밖으로 나가면 나타나는 축약 줄이고, **`fixed top-0` + 자기 `paddingTop: env(...)`** 라 ADR-010
v2 규약에 맞게 쓰여 있다. 홈에도 그대로 쓸 수 있는지 먼저 보고, 맞으면 새로 만들지 않는다.

새로 만든다면 **셸이 붙이는 쪽**이 원칙에 맞다([ADR-007](../decisions/ADR-007-shell-owned-back-navigation.md)
· ADR-010 과 같은 이유) — 화면마다 헤더를 직접 다는 형태는 피한다.

**헤더가 있다고 위 두 문제가 풀리는 것이 아니다 — 불투명해야 한다.** 반례가 이미 코드에 있다:
`src/components/layout/appBar.tsx` 는 상시 `sticky top-safe` 헤더인데도 아무것도 해결하지
못한다. 자기 주석이 이유를 적어 뒀다 — "줄 자체는 여전히 배경을 칠하지 않는다. 화면마다 맨 위
바탕색이 다르기 때문이다". 브라우저가 읽어갈 `background-color` 가 없으면 샘플링 대상이 되지
못하고, `opacity-0`·`/95` 같은 반투명도 무엇을 가져갈지 보장이 없다. 그러므로 이 작업이 만들
헤더의 조건은 둘이다 — **불투명할 것**, 그리고 **전 화면에서 같은 색일 것**.

`appBar` 를 불투명하게 바꾸는 선택지는 3단계와 충돌한다. 제목 판을 앱바 높이만큼 끌어올리는
`-mt-14 pt-14` 는 그 줄이 **투명하다는 전제**로만 성립하기 때문이다. 앱바는 투명한 채로 두고
헤더를 따로 세우거나, 둘을 합치되 상세 화면을 함께 다시 그리거나 — 2단계에서 정할 것은
사실상 이 갈림길이다.

### 3. (상세 포함 시) 제목 판을 앱바 밑에서 시작하게

`src/screens/placeDetailHeader.tsx` — 현재:

```tsx
<header
  data-top-surface
  className="under-app-bar"
  style={{ backgroundColor: typeTint(place.type, 22), backgroundImage: typeHeaderBackground(place.type) }}
>
```

- `data-top-surface` · `backgroundColor`(색을 읽히려고 깔아 둔 통로) · `typeTint` import **삭제**.
- `under-app-bar` → 앱바 높이만큼만 끌어올리는 `-mt-14 pt-14` 로 되돌린다.
  `src/styles/globals.css` 의 `@utility under-app-bar` 도 함께 **삭제**.
- 그러면 제목 판 위에 앱바 줄 높이만큼 크림이 남는다 — 그게 목표다.

### 4. 우회 장치 삭제

`src/components/layout/appShell.tsx` 의 **두 번째 `useEffect`**(`<html>` 배경 동기화, 주석
포함 약 20줄)를 통째로 지운다. 3단계를 했다면 읽을 `data-top-surface` 가 하나도 안 남는다.

### 5. 상태바 글씨를 검정으로

`src/app/layout.tsx`:

- `appleWebApp.statusBarStyle: 'black-translucent'` → 검정 글씨가 되는 값으로. **어떤 값이
  지금 iOS 에서 어떻게 동작하는지 확인하고 넣을 것** — `default` 가 `viewport-fit: cover` 와
  만났을 때 내용이 상태바 밑까지 깔리는지 여부는 iOS 버전마다 보고가 갈린다. 실기기 확인 전에
  단정하지 않는다.
- `viewport.themeColor: '#2e2327'`(잉크) → 페이지 바탕(크림, `--color-neutral-50` 의 실제 값)으로.
  `src/app/manifest.ts` 의 `theme_color` 도 같이 맞춘다(CLAUDE.md 의 "팔레트를 바꾸면" 항목과
  같은 짝 관계다. 팔레트 자체는 안 바꾸므로 아이콘 재생성은 안 한다).

### 6. 남기는 것

`bleed-top-4`(둘러보기 검색 줄, `src/screens/placesPage.tsx`)는 **유지한다.** sticky 줄이
상태바에 붙을 때 자기 블러 배경으로 그 자리를 덮는 용도라 이 작업과 무관하다.
`globals.css` 의 `@utility bleed-top-*` 도 그래서 남는다.

## 문서 갱신 (코드와 같은 단계에서)

- **[ADR-010](../decisions/ADR-010-shell-owned-safe-area.md) v3** — "맨 위 면은 전 화면 크림"
  으로 결정을 좁히고, v2 의 `<html>` 배경 동기화·`data-top-surface`·`under-app-bar` 절을
  "왜 없앴나" 로 바꾼다. `bleed-top-*` 은 남으므로 그 설명은 유지.
  **착수 전 실험 2번이 참으로 나오면 제목이 달라진다** — "왜 없앴나" 가 아니라 "왜 애초에
  동작하지 않았나" 다. 그 실험 결과를 근거로 적을 것.
- **[ADR-003](../decisions/ADR-003-untitled-ui-and-palette.md)** — 히어로가 화면 끝까지 깔리지
  않게 된 것을 한 줄. 팔레트 값은 안 바뀐다.
- **[app-shell-and-state.md](../architecture/app-shell-and-state.md) v10** — 상태바 인셋 절과
  "홈 히어로만 셸의 중앙 정렬 폭을 넘는다" 문장을 함께 고친다.

## 검증

### 착수 전 (실기기, 코드를 고치기 전에)

이 작업은 세 화면(홈·상세·지도)을 건드린다. 그 크기가 정말 필요한지를 **먼저** 가르는
실험 둘이다. 데스크톱에서는 판별 불가능하다.

1. **홈 화면에 추가한 PWA(standalone)로 전 화면 촬영** — "왜 하는가" 2번이 실재하는지.
   크림 화면(준비물·설정)에서 시계·배터리가 읽히면 그 동기 절반은 사라진다. 지금까지 받은
   사진은 전부 Safari 탭(하단 주소창)이라 이 질문에 **아무 정보도 주지 않는다** — 탭 모드는
   `safe-area-inset-top` 이 0 이라 standalone 과 경로가 완전히 다르다.
2. **`collapsingTitleBar.tsx` 의 축약 줄을 `{collapsed && …}` 로 바꿔 Safari 탭에서 재촬영** —
   "왜 하는가" 1번의 원인 후보를 확정한다. 띠가 잉크로 바뀌면 축약 줄이 샘플링을 가로챈 것이
   맞다. 그 경우 이 한 줄이 **이 작업과 독립적인 수정**이 되므로, 확정되면 `docs/bugs/` 에
   BUG 로 승격한다(번호는 그때 붙인다). 실험 후에는 되돌릴 것 — 목표 상태에서는 이 줄이 주는
   크림이 정답이라 조건부 렌더가 오히려 손해다.

2 번이 참이고 1 번이 "읽힌다" 로 나오면 남는 동기는 미관 하나다. 그때는 이 문서를 접고
축약 줄만 고치는 선택지가 열린다.

### 착수 후

`env()` 는 데스크톱에서 항상 0 이라 화면만 봐서는 알 수 없다. ADR-010 의 방법을 그대로 쓴다.

1. `src` 안의 `env(safe-area-inset-top, 0px)` → `59px`, `-bottom` → `34px` 로 **리터럴 치환**.
   fallback 값을 바꾸는 것으로는 안 된다(Chromium 은 인셋을 항상 0 으로 정의해 fallback 을
   쓰지 않는다).
2. 390×844 에서 홈·둘러보기·상세·준비물·지도를 **스크롤 0 과 400px 지점 각각** 촬영.
3. **되돌릴 때 주의** — `src/screens/mapPage.tsx` 의
   `h-[calc(100dvh-60px-env(safe-area-inset-bottom,0px))]` 는 Tailwind 임의값이라 **공백이 없다.**
   일괄 치환으로 되돌리면 공백이 들어가 클래스가 통째로 무효화된다. `git diff` 로 그 파일이
   비었는지 확인할 것.
4. `pnpm lint` · `npx tsc --noEmit` · `pnpm test` · `pnpm build`.
5. 빌드 CSS 확인 — Tailwind functional utility 는 매칭에 실패해도 **CSS 도 에러도 안 낸다.**
   `grep -rho 'bleed-top[^{]*{[^}]*}' out/_next/static/css/` 로 선언이 실제로 생성됐는지 본다.
   Lightning CSS 가 선택자를 `.bleed-top-10,.bleed-top-4{...}` 로 합치므로 정규식을 좁게 쓰면
   있는데 없어 보인다.

#### 실기기 (사용자가 직접) — 작업을 마친 뒤

데스크톱에서는 판별 불가능한 것들이다.

- **iOS Safari 탭 (주소창 아래)** — 홈 상단 띠가 크림으로 다른 화면과 같아졌는지. 이것이 이
  작업의 판별 화면이다(참고 사진: 2026-09-17 — 하단 주소창이 보이는 Safari 탭, 잉크 히어로
  위에 크림 띠. 사진은 레포에 넣지 않았다).
- **홈 화면에 추가한 PWA(standalone)** — 인셋이 0 이 아니라 경로가 완전히 다르다. 상태바 글씨가
  크림 위에서 읽히는지(5단계의 핵심), 홈 히어로 위쪽이 깨지지 않는지.
- **`default` 가 상태바 띠를 무슨 색으로 칠하나** — 내용이 상태바 밑까지 깔리지 **않는** 동작이면
  그 자리는 iOS 가 칠한다. `theme-color`(크림)를 쓰는지 시스템 흰색인지가 갈리는 지점이고,
  흰색이면 크림 본문과 미세하게 어긋난 띠가 남는다. 그때의 선택지는 `themeColor` 를 흰색으로
  맞추는 것이다(팔레트가 아니라 이 값 하나만).
- **상세** — 제목 판 위 크림 띠(인셋 + 앱바 줄)가 어색하지 않은지. 어색하면 `-mt-14 pt-14` 를
  다시 붙여 앱바 줄만큼 색을 올리면 된다. **`useEffect` 는 되살릴 필요가 없다** — 그 위 인셋
  자리는 어느 쪽이든 크림이다.
- **지도** — 여백 0, 타일 높이 안 넘침.

## 종류 카드의 숫자 (2026-09-29)

프로필이 있으면 종류 카드는 **"가능 N · 확인 M"** 을 보이는 글자로 쓰고, 목록 머리는 같은 함수
(`src/lib/eligibilityCounts.ts` 의 `countByLevel`)로 "26곳 · 가능 4 · 확인 3 · 정보 없음 5 · 어려움 14" 를 쓴다.
예전 "7 / 26" 은 ok+cond 합에 이름표가 없어 "7 이 뭐예요?" 가 나왔고, 스크린리더만 "갈 수 있는 곳" 이라
읽어 확인 필요까지 가능으로 부풀렸다. **두 화면이 같은 레벨 이름으로 같은 수를 말하는 것**이 기준이다 —
한쪽만 합산으로 돌리지 않는다. 프로필이 없으면 둘 다 총수만.
