# ADR-012 — 휴대폰 번호를 받는 순간 필요한 것들

> 최종 수정: 2026-09-17 (v1: 신설 — 수집 항목, 인증 수단 분리, 리전, 동의 기록, 파기와 블랙리스트의 충돌)
> 상태: 제안 — 구현 전. 약관·처리방침 문안은 아직 없다.

## 맥락

회원에게 **휴대폰 번호**와 **강아지 이름**을 받기로 했다. 여기서 이 프로젝트의 성격이
바뀐다 — 지금까지 이 앱은 개인정보를 **하나도** 다루지 않았다. 강아지 프로필도 이름 없이
무게·종류만 받아 localStorage 에만 뒀다([ADR-005](ADR-005-dog-profile-eligibility.md)).

휴대폰 번호는 개인정보다. 받는 순간 **약관과 개인정보처리방침이 있어야 하고, 동의를 받아야
하고, 언제 지울지 정해야 한다.** "나중에 붙이자" 가 안 되는 이유는 두 가지다.

- **처리방침은 공개 자체가 의무**다. 서비스를 열어 두고 방침이 없으면 그 상태가 곧 문제다.
- **동의는 소급이 안 된다.** 이미 받아 둔 번호에 대해 나중에 동의를 받으려면 전원에게 다시
  물어야 하고, 연락할 수단이 그 번호뿐이면 순환이다.

그래서 **코드보다 문서가 먼저**다. 이 ADR 은 무엇을 만들어야 하는지의 목록이다.

## 결정

### 1. 인증은 이메일, 휴대폰 번호는 프로필 값

| | 인증 수단 | 프로필 값 |
|---|---|---|
| 이메일 | ✅ 매직링크 / OTP | |
| 휴대폰 번호 | ❌ | ✅ |

SMS OTP 는 유료 발송 사업자를 붙여야 해서 "무료 Supabase" 라는 전제를 깬다. 더 중요한 건
**번호가 인증 수단이 되면 지울 수 없게 된다** — 로그인 키라서 파기 요청이 와도 계정을
통째로 없애는 것 말고는 방법이 없다. 프로필 값이면 그 칸만 비울 수 있다.

### 2. 리전은 **서울(ap-northeast-2)**

해외 리전을 쓰면 개인정보를 국외로 옮기는 것이 되어 별도의 고지와 동의가 붙는다.
서울 리전을 고르면 그 부담이 통째로 사라진다.

**⚠️ 리전은 Supabase 프로젝트를 만들 때만 정할 수 있다.** 나중에 바꾸려면 프로젝트를 새로
만들어 옮겨야 한다. 이 문서에서 가장 되돌리기 어려운 한 줄이다.

### 3. 받는 것을 표로 고정한다

| 항목 | 목적 | 필수 | 보유 |
|---|---|---|---|
| 이메일 | 로그인, 가입 승인 안내 | 필수 | 탈퇴 시까지 |
| 휴대폰 번호 | 본인 식별, 가입 승인 연락 | 필수 | 탈퇴 시까지 (+ 차단 시 해시만 별도) |
| 강아지 이름 | 화면 개인화 | 선택 | 탈퇴 시까지 |
| 강아지 무게·종류·이동수단 | 갈 수 있는 곳 판정 | 선택 | 탈퇴 시까지 |

- **표에 없는 것은 받지 않는다.** "나중에 쓸지도" 로 칸을 늘리면 그만큼 지켜야 할 것이 는다.
- 강아지 이름은 그 자체로는 개인정보가 아니지만 번호와 같은 행에 있으면 함께 보호 대상이다.
  **판정 로직(`eligibility.ts`)은 이름을 쓰지 않는다** — 화면 문구용이라 선택으로 둔다.

### 4. 동의는 버전을 갖는 별도 테이블

```
terms_versions(id, kind('terms'|'privacy'), version, body, published_at)
consents(user_id, terms_version_id, agreed_at)
```

- **버전이 없으면 "약관을 고쳤을 때 누구에게 다시 물어야 하나" 에 답할 수 없다.** 이게
  이 테이블을 따로 두는 유일한 이유다. `profiles.agreed = true` 한 칸으로는 안 된다.
- **필수와 선택을 나눠 받는다.** 한 체크박스로 묶으면 선택 항목까지 필수가 된다.
- **미리 체크된 상태로 두지 않는다.**
- 만 14세 미만은 법정대리인 동의가 필요하다 — 이 규모에서 실무적인 답은 **"만 14세 이상입니다"
  확인 체크박스**다. 연령을 직접 저장하지 않으므로 받는 항목도 늘지 않는다.

### 5. 파기 — 그리고 블랙리스트와의 충돌

목적을 다하면 지운다(탈퇴 = 목적 종료). 그런데 **블랙리스트는 탈퇴 뒤에도 남아야 작동한다.**
남지 않으면 탈퇴 후 재가입으로 그대로 뚫린다. 이건 파기 원칙과 정면으로 부딪히므로
얼버무리지 않고 이렇게 처리한다.

- 보관하는 것은 **휴대폰 번호의 salt 섞은 해시 하나**다. 원문도, 이름도, 이메일도 아니다.
  가입 시 같은 방식으로 해싱해 대조만 하면 되므로 번호를 갖고 있을 이유가 없다.
- 목적은 **부정이용 방지 하나**로 한정하고, **처리방침에 "무엇을·왜·얼마나" 를 명시한다.**
  방침에 안 적힌 채 남아 있는 데이터가 가장 나쁜 상태다.
- 보유 기간을 정해 적는다(무기한으로 두지 않는다).

### 6. 만들어야 할 문서 2종

| 문서 | 성격 | 어디에 |
|---|---|---|
| **이용약관** | 가입 시 동의 | 앱 안 + `terms_versions` |
| **개인정보처리방침** | **상시 공개**(동의와 별개) | 앱 안 + `terms_versions` |

처리방침에 반드시 들어갈 것: 수집 항목·목적·보유 기간(위 3번 표), 파기 절차,
**블랙리스트 해시의 별도 보관**(5번), 처리 위탁(Supabase) 과 그 리전, 이용자의 열람·정정·삭제
요구 방법과 연락처.

**[ADR-011](ADR-011-app-gate-and-supabase.md) 의 한계도 여기에 적는다** — 차단해도 이미
그 기기에 내려간 캐시는 회수할 수 없다는 사실. 불리한 내용이라 빠지기 쉬운데, 빠뜨리면
사실과 다른 방침이 된다.

## 하지 않기로 한 것

- **주민등록번호·생년월일·주소를 받지 않는다.** 이 앱이 하는 일에 필요 없다.
- **휴대폰 번호 원문을 블랙리스트에 남기지 않는다.**
- **강아지 이름을 판정 로직에 쓰지 않는다.** 화면 문구용으로만 둬야 "선택 항목" 이 유지된다.
- **약관 문안을 이 문서에 쓰지 않는다.** 여기는 "왜 이렇게 정했나" 고, 문안은 별도 문서다.

## ⚠️ 확인이 필요한 것

이 문서는 **의무의 내용과 그것이 설계에 미치는 영향**만 적었고, **법 조문 번호는 일부러
쓰지 않았다** — 기억에 의존한 조문 인용은 틀렸을 때 없느니만 못하다.

- 조문 근거와 최신 개정 사항: **law.go.kr** 의 개인정보 보호법 · **개인정보보호위원회(pipc.go.kr)** 의
  표준 처리방침 양식·안내서.
- 개인 개발자가 운영하는 소규모 서비스에 적용되는 범위(안전성 확보조치 등)도 위에서 확인한다.
- 실제 공개 전에 한 번은 사람의 검토를 받는 편이 좋다.
