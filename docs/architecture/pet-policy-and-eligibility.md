## 개요

장소마다 반려동물 이용 조건이 사람이 쓴 문장(`petPolicyText`)으로 있다. 이 문서는 두 층을 다룬다.

1. **파서(구현됨)** — 문장 → `TPetPolicy`. 화면 배지와 필터가 쓴다.
2. **판정(구현됨, v1)** — `DogProfile × TPetPolicy → Eligibility`. 앱의 목적 그 자체다(→ [CONCEPT.md](../CONCEPT.md)).

```mermaid
flowchart LR
  T["petPolicyText<br/>(원문)"] -->|parsePetPolicy| P[TPetPolicy]
  P -->|toPetBadges| B[배지: ok / cond / warn]
  P -->|PET_FILTERS| F[둘러보기 필터]
  D[TDogProfile] -->|judgeEligibility| E[TEligibility<br/>ok · cond · unknown · hard]
  P --> E
  T -->|원문 공개(시드)만 병기| UI["화면: 홈·목록·상세·지도"]
  P -->|policyEvidence — 블로그 출처| UI
  E -->|배지·정렬·판정 카드| UI
```

## 1. 파서 — `src/lib/petPolicy.ts`

### 출력 `TPetPolicy`

| 필드 | 의미 | 값이 없을 때 |
|---|---|---|
| `indoor` | `free`(실내 자유) / `cage`(실내는 케이지·이동가방·유모차) / `outdoorOnly` / `unknown` | `unknown` — 숙소는 대부분 여기 |
| `weightLimitKg?` | "10kg 이하" 같은 상한 | 없으면 제한 언급 없음 |
| `smallDogOnly` · `mediumDogOk` · `largeDogOk` | 크기 언급 | 전부 false 면 크기 언급 없음 |
| `largeDogNo` | **"대형견은 어려워요"·"대형견 입장 불가"** — 크기의 부정. `largeDogOk` 한 칸으로는 "불가" 와 "언급 없음" 이 둘 다 false 라 따로 둔다. 둘이 같이 걸리면 `largeDogOk` 를 끈다(제한을 믿는다). '대형견 제한 없음' 은 허용이라 걸리지 않는다. '어려워요' 에는 '어렵' 이 없어(ㅂ 불규칙) 정규식이 둘 다 적는다 | `false` |
| `maxDogs?` | 마릿수 상한. "견수 제한 없음" 처럼 숫자가 없으면 비움 | 비움 — 숫자를 지어내지 않는다 |
| `leash` · `callFirst` | 리드줄 필수 / 사전 전화 | false |
| `petDays?` | 동반이 **그 요일에만** 된다(`['수']`, 한 글자 요일, 원문 순서). 정규식은 한 문장 안에 요일(`매주 X요일`·`X요일에만`·`X·Y요일`)과 동반·반려·애견 낱말이 같이 있고 휴무·불가 낱말이 없을 때만 세운다. **휴무일은 담지 않는다** — "월요일 휴무" 가 "월요일만 동반" 으로 뒤집히면 쉬는 날에 가라는 안내가 된다. AI 가 준 요일은 원문에 `X요일` 로 없으면 뺀다(`correctPetPolicyFacts`, 다 빠지면 null) | 없음 — 요일 제한 없음 |
| `feeFree` · `feeText?` | 추가 요금 없음 / 요금 원문(= `feeLines[0]`, 옛 화면 호환). **배지는 `feeText` 가 아니라 `feeLines` 전부로 만든다** | |
| `feeCharged` | 추가 요금이 **있다고만** 읽었다(AI `feeFree: false`, 금액 문장 없음). 정규식은 세우지 않는다 | `false` |
| `noInfo` | 원문이 비었거나 "정보 없음" — 빈 원문은 2026-09-28 부터 실제로 여기 걸린다(BUG-008 전에는 문자열만 봤다). **다른 조건이 한 줄이라도 읽히면 서지 않는다** — 맘앤도그 "정보 없음. (문의해보시면 …) 대형견도 동반 가능!!" 은 `largeDogOk` + `callFirst`(남은 "문의해 보세요" 를 C6 로) 다. 전엔 '확인된 정보가 없어요' 판정 옆에 '대형견 OK' 칩이 떴다(14 W261006.3). 전화 확인만 붙은 "정보 없음" 은 그대로 여기 | |
| `unread` | 원문이 **있는데** 이 표의 조건이 하나도 안 섰다(정규식도 AI 도 못 읽음). "애견동반 가능해요!" 처럼 **일반 허용 문장만** 있으면 읽은 것으로 본다 — 단 그 문장에 야외·kg·케이지·요금 같은 제한 암시어가 섞이면 일반 허용이 아니다. 필드를 새로 더하면 `readNothing` 에도 더한다(빠지면 읽은 원문이 '못 읽음' 이 된다) | `false` |
| `genericOnly` | 원문이 **일반 허용 문장뿐**이다 — `unread` 의 반대편(읽었는데 조건이 없다). C9 가 `verified` 와 같이 본다. AI 판단 경로에서는 AI 가 읽은 조건 · `notes` · 정규식에만 남는 허용 단서(`outdoorFree`·`unlimitedDogs`)가 하나라도 있으면 아니다 | `false` |

| `seating` | 식당·카페다(실내·야외 자리를 고르는 곳). `verified` 처럼 **장소에서** 온다 — 파서는 늘 `false`, `toPlaceEntry`(`placeDerive.ts`, 런타임)의 `withPlaceType` 이 얹는다. C12 가 숙소를 가르는 데만 쓴다 | `false` |
| `notAllowed` | "애견동반은 안됩니다" 처럼 주어(애견·반려견·강아지…)+동반/출입/입장 뒤에 불가·안 됨·금지. 견종 뒤의 '불가'(대형견 불가)는 아니다 | 배지 '동반 불가' |
| `tiers` | 계단식 무게·마릿수 조건. `{ maxWeightKg?, weightInclusive?, maxDogs?, source }[]`. 웨스티하우스 → `[{10,미만,2},{20,미만,1}]`. `weightLimitKg`/`maxDogs` 는 여기서 최댓값을 뽑아 파생(화면·필터 호환) | `[]` |
| `outdoorFree` | "실외는 자유", "실내외 모두 가능" 이거나 `indoor==='outdoorOnly'` — 야외 이용이 열려 있음 | `false` |
| `unlimitedDogs` | "견수 제한 없음" 처럼 숫자 없이 마릿수 무제한. `maxDogs` 가 비어 있어도 필터가 "2마리 이상" 으로 잡을 수 있게 한다(백화stay) | `false` |

| `sources` | 규칙별 근거 문장(원문 그대로). `indoor`\|`largeDogOk`\|`largeDogNo`\|`mediumDogOk`\|`smallDogOnly`\|`callFirst`\|`leash`\|`feeFree`\|`noInfo` 키만 있고, 실제로 해당 규칙이 걸린 곳만 채워진다. 판정 층이 `reasons[].quote` 로 쓴다 | `{}` |

### 규칙 테이블

파일 상단에 정규식 테이블로 모여 있고 **위에서부터 먼저 걸리는 규칙이 이긴다.**
"실내외 모두 가능하지만 실내에서는 유모차 필요" 처럼 두 조건이 한 문장에 있으므로 더 제한적인 쪽(`outdoorOnly` → `cage` → `free`)을 먼저 본다.
새 표현이 나오면 정규식 한 줄을 추가하고 `pnpm test` 로 확인한다(`src/lib/petPolicy.test.ts`).

### 파서가 하지 않는 것

- **판정하지 않는다.** "대형견은 야외만" 을 `largeDogOk=true, indoor=outdoorOnly` 로 쪼갤 뿐, 우리 강아지가 갈 수 있는지는 말하지 않는다.
- **추측하지 않는다.** 숫자·상한이 안 적혀 있으면 비워 둔다. 필터 결과가 실제보다 적을 수는 있어도 틀린 "가능" 은 내지 않는다.
- 그래서 화면은 **항상 원문을 함께** 보여준다(→ [ADR-004](../decisions/ADR-004-pet-policy-parser.md)).

## 2. 배지와 필터 (구현됨)

- `toPetBadges(policy)` → `{ label, tone: 'ok' | 'cond' | 'warn', axis: TBadgeAxis }[]`. 카드·상세 상단에 3개 이하로 보인다.
  순서는 이 함수 하나가 정하고 그것이 곧 사이트의 순서다: 동반 불가 → 실내 → **요금(줄마다 하나)** → 크기 → 무게 → 마릿수 → 리드줄 → 확인 필요.
  **무게 구간마다 마릿수가 다르면 무게·마릿수 칩 대신 구간 칩이다**(`dogCountTiers` · `dogTierBadgeLabel` — 웨스티하우스 `10kg 미만 2마리` · `20kg 미만 1마리`).
  `20kg 미만` · `최대 2마리` 로 접으면 '최대 2마리' 가 H2 "20kg 미만은 1마리까지예요" 와 반대로 읽혔다(14 W261013.1b). 공개 템플릿의 마릿수 줄도 같은 구간으로 말하고,
  카드 거르기(`REASON_BADGE`)는 H1 → 가장 넓은 구간 칩, H2 → **그 줄이 말한 구간** 칩이다 — 구간은 강아지에 따라 갈려 줄과 같은 문장 함수(`tooManyText`)로 찾는다.
  구간이 하나거나 마릿수가 같으면 두 칩이 그대로 맞다.
- **카드는 요금 줄을 첫 줄만 세운다**(`limit` 이 주어진 뷰 — 카드·지도 시트·근처 목록). 요금은 개수 상한이 없고 순서에서
  크기·확인 필요보다 앞이라, 그대로 자르면 경고 배지가 `+N` 뒤로 숨는다. 접힌 수는 거른 뒤가 아니라 전부에서 센다.
  화면 글자는 `+N` 이 아니라 `조건 N개 더` 다 — 숫자만으론 무엇을 접었는지 몰랐다(14 W261013.14l).
  프로필이 있으면 그 한 줄은 첫 줄이 아니라 **가장 무거운 아이가 들어가는 줄**이다(`dogFee.ts` 의 `feeChipForWeight`, 07 U5).
  몸무게로 갈리지 않는 기본 줄(마리당)이 있으면 구간 밖일 때 그 줄, 줄이 전부 구간인데 안 들면 금액을 고르지 않고 "10kg 까지 요금표",
  하한 줄만 있고 그 아래면 칩을 뺀다 — 원문이 그 몸무게의 요금을 말하지 않는다.
  **마릿수 조건도 같은 자리에서 본다** — 캄 `2마리 또는 10kg 이상 4만원` 은 5kg 두 마리에게도 걸린다. 몸무게만 보면 칩은
  `1마리당 3만원`, 요금 한 줄은 `4만원` 이라 한 카드가 두 금액을 말했다(07 U5 후속). 상세(`limit` 없음)는 그대로 전부다.
- `axis` 는 **사이트가 그 밖에는 안 쓴다**(한 줄에 전부 세운다). `/admin` 검수 표가 `동반 조건`·`강아지 요금`·`필요 장비` 세 열로 가르는 데 쓴다
  (`adminPreview.ts` 의 `policySplit`). 라벨로 가를 수 없어서 값에 싣는다 — 요금 배지의 라벨은 요금 줄을 정규화한 문장이라("1마리당 2만원") 라벨만으로는 축을 알 수 없다.
- **요금 배지 라벨은 `normalizeFeeLines`(`scripts/lib/feeLine.mjs`)를 거친다.** `feeLines` 자체는 원문 그대로 두는데, 판정(C5 의 `N kg 이상`·구간 상한)과
  `formatDogFee` 가 같은 배열을 앵커된 정규식으로 읽고 시드 파싱 결과가 테스트에 못 박혀 있어서다. 정규화 결과는 그 정규식들이 읽는 모양(`1마리당 N만원`·`A~Bkg N만원`·`Nkg 이상`)을
  그대로 지키므로, 분석 시점에 저장되는 AI 요금 줄은 정규화된 채로 들어가도 판정·요금 문구가 깨지지 않는다. 한 줄에 금액이 둘 이상이면 기준마다 나눈다 — 경계는 쉼표·마침표 뒤 공백과 **공백으로 둘러싸인** `/`·`·` 뿐이다(`중·대형견`·`2만원/박` 에서 자르면 중형견 요금·단위가 떨어져 나간다). 금액 없는 조각이 `kg`·`마리` 조건이면 다음 기준에 붙이고(C5 가 `10kg 이상` 을 읽는다), 조건 없는 설명문만 버린다. 분석 시점에 저장된 줄은 되돌릴 수 없으니 분할 규칙을 넓힐 때는 이 점부터 본다.
  `'gear'`(챙겨 갈 것)만 **값으로 갈린다**: `indoor: 'cage'`("케이지 필요")는 실내 판단에서 나오지만 사람이 할 일은 가방을 챙기는 것이라 장비 축이고,
  `free`·`outdoorOnly` 는 챙길 것이 없어 `'indoor'` 로 남는다.
- `PET_FILTERS`(`src/lib/placeFilters.ts`) 는 종류별로 다르다. 식당·카페는 실내/케이지/대형견/리드줄, 숙소는 추가요금/대형견/2마리 이상.
  원문에 적힌 정보의 종류가 다르기 때문이다.
  **이 칩들은 판정이 아니라 원문으로 거른다** — 축이 다르다. 판정은 원문이 막지 않으면 연다(마릿수가 없으면 두 마리도 '갈 수 있어요'),
  칩은 원문에 적힌 곳만 남긴다. 그래서 두 마리 프로필로 '2마리 이상' 을 켜면 '갈 수 있어요' 숙소 4곳(돌담연가·나미브·스테이모슬·캄 — `maxDogs` 없음)이
  빠진다. 칩을 판정에 맞추지 않고 **이름표가 축을 말하게** 했다: 시트 묶음 이름 "원문에 적힌 조건" + "적혀 있지 않으면 '갈 수 있어요' 인 곳도 빠져요". 22 D-8 에서 섹션이 2열 체크박스가 되며 설명은 "글에 적힌 곳만 남아요" 한 줄로 줄었다 — 판정 '갈 수 있어요' 와 다르다는 말은 섹션 이름 + 그 줄이 한다(설명 줄이 남은 섹션은 이것뿐이다).
  같은 이유로 '실내 동반 OK'(원문으로 거름, 카페 24 → 22)와 '실내 자리 필요'(곳은 그대로, 판정을 실내 기준으로)가 이름이 비슷해 섞였다 —
  후자가 사는 "우리 강아지 기준" 묶음에 설명 두 줄(14 W261007.7 → W261019.1) — **22 A·B review R-2 에서 한 줄로**: "야외만 되는 곳은 어디서나 어려움으로 봐요". '실내 자리 필요' 는 필터가 아니라 설정(몸무게 같은 판정 입력)이라
  다른 조건을 가리키는 둘째 줄을 걷었고, 어느 초기화도 그것을 끄지 않는다. 아래 두 줄의 이력과 실측(둘째 줄의 약속)은 그 판단의 근거로 남긴다. md+ 의 펼친 줄(`bar`)엔 이름표가 없어 이 말이 없다.
  처음엔 방식("곳을 빼지 않고, 실내 자리 기준으로 다시 판정해요")을 적었는데 평가 3/6 이 무엇이 바뀌는지 못 읽어(반복 4회) **결과**로 바꿨다 —
  "켜면 야외 자리만 되는 곳은 '어려움', 실내 얘기가 없는 곳(C12)은 '확인 필요'가 돼요 · 앱 전체에 남아요" + "실내까지 같이 갈 곳만 보려면
  위에서 '갈 수 있는 곳만'을 골라요 · '실내 동반 OK' 는 강아지와 상관없이 걸러요"(22 D-6 에서 '켜요' → '골라요' — 세그먼트가 됐다). 둘째 줄은 약속이라 데이터로 확인했다: 켠 채 `ok` 로 남는 식당·카페는
  전부 `indoor` 가 `free` 거나 이 아이의 수단으로 드는 `cage` 다(91곳 × 수단 넷 × 5·25kg, 어긋남 0 — H6·C4·H4 가 야외 갈래를 어려움으로, C12 가 모르는 실내를 확인으로 올린다).
  **둘은 켜도 같은 말이 아니다** — '실내 동반 OK' 는 `cage` 를 그대로 남겨, 이동 수단 없는 아이에게 H5 '어려움' 인 케이지 필수 곳도 목록에 선다.
- **숙소 환경 필터**(`ENV_FILTERS` — 독채 · 마당 있음 · 울타리 마당 · 계단 없음)는 **판정에 들어가지 않는다.** 갈 수 있는지와 무관한 선호라
  `eligibility.ts` 를 지나지 않고, 화면에서도 반려동물 조건과 **다른 묶음**("숙소 환경")으로 그린다 — 한 줄에 섞으면 "대형견 OK" 와 "마당 있음" 이 같은 무게로 읽힌다(08 T2.3).
  true 로 확인된 곳만 걸린다(모르는 곳을 넣으면 "계단 없음" 에 계단 있는 곳이 섞인다). 데이터에 걸리는 곳이 없는 칩은 그리지 않는다 — 시드에는 울타리·단층 문장이 없어
  지금은 `독채`·`마당 있음` 둘만 선다. 값은 `TPlaceEntry.environment`(AI `stay.environment` 칸마다 우선 + 정규식, `scripts/lib/stayEnvironment.mjs`).
- **객실 조건**(`indoorRoom` 객실 안 · `furniture` 침대·소파 — 같은 `environment` 의 칸)도 판정에 들어가지 않지만, 자리는 숙소 환경 절이 아니라 **판정 카드의 근거 칸**이다
  (`PlaceDetailRoomConditions`, 원문 아래 · 확인 날짜 위). "갈 수 있어요" 를 본 대형견 보호자가 다음으로 묻는 말이 "객실 안이냐, 마당만이냐" 라서다(14 W261013.11).
  원문이 말한 칸만 그리고 모르면 줄째 없다. "대형견은 마당만" 처럼 **크기로 갈리는 문장은 칸에 오지 않는다** — 판정이 다뤄야 할 갈림이고 아직 규칙이 없다(ADR-017 결정 12).

## 3. 판정 — 구현됨

### 입력 `TDogProfile` (`src/types.ts`)

| 필드 | 타입 | 왜 필요한가 |
|---|---|---|
| `dogs` | `{ name: string; weightKg: number }[]` (1~3) | 마리별 이름·몸무게. 무게 상한 비교는 **최댓값**(`maxWeightKg`, `dogProfile.ts`), 마릿수는 `length`. 28kg+17kg 를 `count=2, weightKg=28` 로 뭉개면 실제보다 후하게 판정한다(디자인 리뷰 §1③). 이름이 마리별인 이유는 [ADR-005 v3](../decisions/ADR-005-dog-profile-eligibility.md) |
| `carrier` | `'none' \| 'bag' \| 'cage' \| 'stroller'` | 케이지 필수인 곳에서 슬링백을 케이지로 오해하면 위험하다(리뷰 §1③) — 넷으로 나눠 판정을 갈랐다 |
| `sizeOverride?` | `TDogSize` | 몸무게 기준 자동 계산(소형 <10kg · 중형 10~25kg · 대형 >25kg)이 원문의 "대형견" 과 어긋날 수 있어 프로필 폼의 "크기 수정" 으로 고칠 수 있다 |

`needsIndoor`(실내 자리가 꼭 필요한지)는 프로필이 아니라 **여행 정보**라 스토어의 별도 토글(`useAppStore.needsIndoor`)로 분리했다 — 계절이 바뀌면 강아지는 그대로인데 필요한 자리는 바뀐다(리뷰 §1②).

프로필은 기기 안(localStorage, `useAppStore`)에만 둔다. 마리별 프로필(성향·견종)은 범위 밖.

### 판정 규칙 — `src/lib/eligibility.ts` 의 `RULES`

**"먼저 걸린 규칙이 이긴다" 던 초안과 달리, 전부 평가해 가장 센 레벨을 채택한다** — 한 문장에 여러 조건이 섞인 원문(예: "실내는 케이지, 실외는 자유")에서 근거 하나를 놓치지 않기 위해서다. 레벨은 hard 하나라도 있으면 hard, 아니면 `noInfo` 면 unknown, 아니면 cond 있으면 cond, 그 외 ok. reasons 는 심각도순(hard→cond→unknown→info)으로 정렬한다.

| # | 조건 | 레벨 | 문구 |
|---|---|---|---|
| H0 | `notAllowed` | hard | "반려견 동반이 안 된다고 적혀 있어요" — 강아지 조건과 무관 |
| H1 | `tiers` 중 무게 조건이 있는 칸이 있는데, 최댓값 몸무게가 그 어느 칸에도 못 들어감 | hard | "{이름}({몸무게}kg)는 {N}kg {미만/이하} 조건을 넘어요" · 여럿이면 "{이름(kg)}·{이름(kg)} 모두 …" — 한도를 넘는 아이만 적는다 |

**{수단}** 은 `cageGearNoun` 하나가 정한다 — 실내 근거(+ 다음 문장)가 적은 것: 이동가방 · 유모차 · 이동가방이나 유모차, 아무것도 안 적었으면 케이지. 수단 칩(`cageBadgeLabel`)이 같은 이름이라("이동가방 필요" · 둘이면 폭 때문에 "이동가방·유모차 필요") 카드의 이유 줄이 수단을 말하면 그 칩이 빠진다(`REASON_BADGE`). 예전엔 줄이 늘 '케이지' 라 칩과 줄이 다른 조건처럼 읽혔다(14 W261013.14g).

### 요금 — `formatDogFee(policy, dog)` (`src/lib/dogFee.ts`)

목록 카드·상세의 info 근거가 **같은 문자열**을 그대로 출력한다(예전에는 화면이 이름을 따로 붙였다). 원칙은 파서와 같다 — **숫자를 지어내지 않는다.** 마릿수만큼 곱해도 되는 것이 원문에서 확실할 때만 곱한다.

뽑고, `sumByRules` 가 그 칸으로 계산한다. 마리마다 몸무게에 맞는 마리당 줄을 골라 더하고(`fromDog` 앞 순번은 0원), 청소비(`flat`)는 한 번 더한다.
물러나는 경우: 금액이 빈 줄이 하나라도 있음(`또는`·범위 금액) · 몸무게가 어느 줄에도 안 들어감(19.5kg) · 한 마리에 줄이 둘 맞음 · 1박당과 한 번이 섞임 · `maxDogs` 초과 · **두 마리 이상인데 쓴 줄의 label 이 basis 를 말하지 않음**(아래).

`maxDogs` 가드는 마리당 곱셈과 구간 합산 양쪽에 걸린다. 구간 합산에서 "안 쓴 구간 줄" 은 조건이 아니라 같은 요금표의 다른 칸이라 가드 대상이 아니다. 줄을 고르는 순서는 예전 `feeForDog` 그대로다: 최대 몸무게가 들어가는 구간 줄 → 구간이 아닌 첫 줄 → 없으면 비운다. 한 마리라도 구간 밖이면 합산하지 않고 이 순서로 물러난다 — 28kg 강아지에게 "1~5kg 1만원" 을 이름까지 붙여 확정된 숫자처럼 보여주지 않기 위해서다. 금액은 만원 단위 소수 1자리(15000 → "1.5만원"), 1만 미만은 "5,000원".

**이름은 곱셈이 성립했을 때만 붙인다.** 곱하지 못한 줄은 "우리 강아지 기준" 이 아니라 원문을 옮긴 것이라 "적힌 요금 · …" 으로 연다(v41 까지 "원문 요금" — '원문' 은 우리 쪽 말이었다) — "대장이와 초코 · 청소비 5만원" 은 우리가 낼 돈이 확정된 것처럼 읽혔다. 그리고 **판정이 어려움(hard)이면 요금 자체를 싣지 않는다**(`fee` 도, I1 근거도) — 못 간다는 곳에 붙은 요금은 답이 아니라 소음이다. **받아 주는지가 아직 열려 있으면**(C5·C10) 요금 앞에 "받아 준다면" 을 붙인다 — "보리는 5만원" 바로 밑의 "대형견 언급이 없어요" 는 금액이 확정이고 크기만 물으면 되는 것처럼 읽혔다. 야외 자리(C1·C4)·가방(C2·C3)·전화 먼저(C6)·예방접종(C8)은 받아 주는 곳이라 붙이지 않는다.

**두 마리 이상이면 합계라고 말하고, 합계의 근거가 화면의 label 에 없으면 합치지 않는다**(14 W261013.4). 이름만 붙은 금액("콩이와 해피는 2만원 (동반 2만원)")은 합계인지 1마리당인지 안 읽혀, 곱하거나 더한 다두 줄은 전부 "… 2마리 합계 4만원 (1마리당 2만원)" 꼴이다(1마리 줄은 그대로). 구조 경로(`sumByRules`)는 두 마리 이상일 때 **쓴 줄의 label 이 basis 를 말할 때만** 합친다(`basisStated` — 마리당은 label 에 '마리' 가 있거나 몸무게 구간 줄, 한 번은 청소비·객실·1회). basis 는 모델이 둘 중 하나를 꼭 고르는 칸이라 본문이 말하지 않아도 채워진다 — 선흘안 "1박당 2만 원 견추비" 가 perDog 로 와 두 마리에 "1박 4만원" 이었고(추출 프롬프트 예시 `FEE_EX.perNight` 가 label "1박당 2만원" + perDog 였다 — W261013.4a 에서 "1마리당 1박 2만원" 으로 고쳤다), 협재현 "애견동반 추가 요금 2만원" 은 flat 으로 와 이름 붙은 "2만원" 이 합계로 읽혔다. 그때는 "적힌 요금 · 1박당 2만원 (합계인지 1마리당인지 적혀 있지 않아요)" — 정규식 경로가 같은 모양("(2만원 추가)")을 곱하지 않고 물러나는 것과 같다: **AI 경로가 같은 모호함에 정규식보다 더 단정하지 않는다.** 요금 문구는 런타임 계산이라 블로그 행도 재계산 없이 바뀐다.

이 방어가 label 의 '마리' 하나를 믿으므로 **label 이 원문에 없는 마리당을 말하면 그 방어까지 속는다**(14 W261013.4a). 그래서 프롬프트는 label 의 '1마리당'·'마리당' 을 본문에 그 말이 있을 때만 쓰라고 하고(본문이 어느 쪽인지 말하지 않으면 basis 는 perDog 그대로 — flat 으로 두라고 하지 않는다, `feeTableTopKg` 가 basis 로 거른다), 원문 대조(`correctPetPolicyFacts` 의 요금 줄)는 label 의 마리당 꼴(`마리당`·`마리마다`·`1견당` — 맨 `마리` 는 아니다, 선흘안 "최대 2마리까지" 는 한도다)이 원문에 없으면 **그 말만 지운다** — 금액은 원문 그대로라 계산에서 빼면 한 마리 "1박 2만원" 까지 잃고, 남긴 '1마리당' 칩은 사람이 곱하게 한다. label 에 마리가 없는 perDog 줄(선흘안)은 가드가 건드리지 않는다 — 두 마리를 안 합치는 것은 위의 `basisStated` 몫이다.
곱하지 못한 줄의 금액 범위 하이픈은 칩과 같은 물결로 쓴다(`stripLine` — "1마리당 1-2만원" → "1~2만원", 줄 전체를 정규화하지는 않는다: "숙박일 관계없이" 가 사라진다). 목록 카드는 **요금 줄이 있으면 고른 요금 칩을 뺀다**(`PetBadges` 의 `feeLine`) — 글자 그대로 들어 있을 때만 빼던 동안 "두부는 1만원 (1~5kg)" 밑에 `1~5kg 1만원` 이, "1-2만원" 줄 밑에 `1~2만원` 칩이 또 섰다(ux-expert-11). 지도 시트·근처 장소는 요금 줄이 없어 칩이 그 자리다.

**단위를 모르는 요금**(`feeUnitNote`, 08 T5.1) — 시드 숙소 16곳 중 15곳이 "1마리당 3만원" 처럼 1박마다인지 한 번인지를 말하지 않는다. 2박이면 두 배일 수 있는데
한 줄은 확정된 금액처럼 읽혀서, 상세의 요금 줄 밑에만 "1박 기준인지는 적혀 있지 않아요" 를 붙인다(v49 까지 "원문에 없어요" — 블로그 출처는 원문을 화면에 내지 않는다). 요금 한 줄에 섞지 않는 것은 카드·상세가 같은 문자열이라는 계약 때문이고,
카드에 따로 달지 않는 것은 숙소 거의 전부라 소음이어서다. 안 붙는 때: 숙소 아님 · 요금 줄이 없음(어려움·추가 요금 없음) · 구조의 `perNight` 가 참 ·
원문이 단위를 말함(`1박`·`박당`·`1회`·`한 번`·`관계없이` — 그리너리빌리지의 "숙박일 관계없이 청소비" 는 한 번이라는 말이다). `청소비` 낱말만으로 한 번이라 보지 않고,
`perNight: false` 도 근거로 쓰지 않는다 — 원문이 말하지 않을 때도 false 다. 단위를 데이터 칸(`feeUnit`, 운영자 입력)으로 받는 쪽은 아직이다(08 T5.1 뒤 절반).

### 한국어 호칭 — `src/lib/korean.ts`

이름이 들어가는 문장은 전부 이 헬퍼를 거친다. 자리마다 따로 구현하면 한 곳만 고쳐져 어긋난다.

- `dogCallName(name)`: 보호자가 부르는 이름. 받침으로 끝나면 '이' 를 붙인다(우현 → 우현이). 받침이 없으면 그대로라 이미 '악동이' 로 등록한 이름에 '이' 가 겹치지 않는다.
- `dogCallNames(names)`: 여러 마리를 한 덩어리로 — "악동이" / "악동이와 두부" / "악동이, 두부, 콩이". **조사는 붙이지 않는다** — 호출부가 문맥에 맞는 조사를 `withJosa(word, '은/는' | '이/가' | '을/를' | '과/와' | '이랑/랑' | '아/야')` 로 붙인다. 그래야 "악동이와 두부**는** 갈 수 있어요" 와 "악동이와 두부**랑** 제주 어디 갈까요?" 가 한 함수에서 나온다.
- `dogNamesAsWritten(names)`: 적은 이름 그대로 같은 꼴로 묶는다("보리, 단풍, 깜지"). **이름만 서는 자리**(설정 「우리 강아지」 카드 제목)와 **방금 적은 이름을 되비추는 자리**(`/dog` 저장 알림 "○○ 기준으로 바꿨어요")는 이것을 쓴다 — 거기서 '단풍' 이 '단풍이' 로 보이면 적은 이름이 바뀐 것으로 읽힌다(14 W261010.33h). 조사가 붙어 문장 안에서 부르는 자리(인사·판정 머리글·요금·공유 글)는 `dogCallNames` 그대로다 — 보통명사 이름(단풍·보리·콩)은 '이' 가 없으면 "단풍은 갈 수 있어요" 가 낙엽 이야기로 읽힌다.
- 받침 판별은 한글 완성형(U+AC00–D7A3)만. 영문·숫자는 받침 없음으로 보고 뒤 조사를 쓴다("Coco는") — 발음을 추측하지 않는다.

### 화면 반영 (구현됨)

- 목록·지도 카드: 판정 배지 하나를 종류 색 옆에. 정렬은 ok → 야외 → cond → unknown → hard — 야외는 레벨이 아니라 cond 안의 앞자리다(`isOutdoorSeatOnly`, 요약 칸과 같은 순서). 배지 라벨은 문장형("갈 수 있어요 / 확인이 필요해요 / 정보가 없어요 / 이용하기 어려워요"). 판정 배지가 있는 줄에서는 원문 배지 "확인된 정보 없음" 을 뺀다(`PetBadges hideNoInfo`) — 같은 말을 두 번 하지 않기 위해
  (`src/lib/sortByEligibility.ts`, `src/components/eligibilityBadge.tsx`).
- 상세: 판정 + 근거 문구(`reasons[].quote`)를 판정 카드로, 그 아래 원문 카드에서 강조
  (`src/screens/placeDetailEligibilityCard.tsx`).
  **근거 칸이 원문을 그리는 것은 원문 공개(`petPolicyTextPublic`, 시드)인 곳만이다**(v49, ADR-017 결정 13) — 블로그 출처는 원문이 블로거의 문장이라 그 자리에
  판단에서 만든 줄(`publicPolicyLines`) + AI 안내(지문이 맞을 때, 없으면 가드를 지난 notes) + 「후기에서 원문 보기」 링크(액션 줄 「후기」 와 같은 글 — v64)를 그린다(v59 — 출처 설명 문장은 없다, AI 정리 안내는 카드 맨 아래 공통 줄)(`policyEvidence`,
  `src/screens/placeDetailPolicyText.tsx`). 이름표도 「원문」 이 아니라 「정리한 조건」. 템플릿 줄이 0개인 곳(동반 불가 · 못 읽음 · 일반 허용 문장뿐)은 빈 칸 대신 상태 한 줄 —
  못 읽음은 C7 과 같이 "원문에서 확인해 주세요" 이고 그 원문이 「후기에서 원문 보기」 링크다. 그래서 판정은 공개 플래그를 모른다(목록·지도·홈이 같은 판정을 쓴다).
  인용(`quote`)은 원문 조각이라 블로그 출처에선 강조할 자리가 없어 화면에 나가지 않는다. **배지의 `sourceText` 는 화면에 나가는 글**(`evidenceText`)이다 —
  원문을 넘기면 요금 칩이 "본문에 이미 있다" 며 숨는데 그 본문이 화면에 없다.
  **머리글은 근거가 같은 말을 할 때 근거를 따른다**(`headlineFor`) — cond 근거가 전부 야외 자리 규칙(C1 야외 자리만 · C4 실내 케이지·야외 자유 · H4 의 cond 갈래, `isOutdoorSeatOnly`)이면 "야외 자리에서 갈 수 있어요", 그 밖의 cond 는 목록 배지와 같은 "확인이 필요해요". "확인해야 알 수 있어요" 바로 아래 "야외 자리만 가능해요" 가 오면 머리글과 근거가 싸웠다. 규칙 판별은 문구가 아니라 근거에 실린 규칙 ID(`TReason.rule`)로 하고, 요금(I1)은 세지 않는다.
  **unknown 은 이름을 빼고 장소를 주어로 말한다**(`verdictFor`, 공유 글도 같은 함수) — "이곳은 반려견 동반 조건이 공개돼 있지 않아요". unknown 은 `noInfo` 에서만 생기고 강아지 조건과 무관한데, "보리는 …" 으로 시작하면 보리를 기준으로 무언가 판정한 것처럼 읽혔다. 상세 카드는 머리글과 같은 말인 U1 근거를 목록에서 뺀다.
- 둘러보기 필터 시트: **강아지 기준 세그먼트 [전부][어려운 곳 빼고][갈 수 있는 곳만]** + '실내 자리 필요' 스위치(식당·카페, `src/screens/placesPageFilterSheetDog.tsx`, 22 D-6). 두 칩('갈 수 있는 곳만' · '어려운 곳 숨기기')은 한 축이었다 — 둘 다 켠 상태는 '갈 수 있는 곳만' 과 같은 목록이다(가능 + 야외만 남으면 어려움은 이미 빠진다). 스토어·걸러 내기는 그대로 두 플래그이고 화면만 한 단계로 읽는다(`lib/placesPageDogStep` — 둘 다 켜져 있으면 '갈 수 있는 곳만', 고르면 하나만 남는다). 홈 동네 카드는 여전히 `onlyReachable` 만 켜서 남은 숨김과 함께 켜질 수 있는데, 그때 켠 조건 칩도 '갈 수 있는 곳만' 하나다(`placesPageChips`). 섹션 제목은 강아지 이름('두부 기준' · 여럿이면 '우리 강아지 기준'). md 부터 펼친 판은 아직 칩 셋(`placesPageEligibilityToggles`, 22 D-10 에서 같이). 칩에 수는 없다(22 D-5) — 숨기는 수를 이름 뒤에 싣던 것(14 W261013.8)은 걷었다. 어려움 0곳 목록에서 눌러도 결과 버튼 수가 그대로인 것은 받아들였다. 판정만 바꾸는 '실내 자리 필요' 의 결과는 시트 하단의 판정 셈 줄이 보였는데(`levelCountParts`, 14 W261013.8) 22 D-9 에서 걷었다 — 스위치 밑 설명 한 줄(22 A·B review R-2 — 설정이라 결과만)이 말로 대신하고, 셈은 시트를 닫으면 목록 머리가 같은 조각으로 보인다. 초기화는 이 값을 끄지 않는다(설정).
- 목록 카드: 요금 줄 아래 근거 한 줄(`primaryReason` — **판정을 정한 근거**). 7곳을 다 눌러야 왜 "확인" 인지 알던 것을 목록에서 읽게.
  ok 는 판정을 정한 근거가 없어 줄이 없지만, 몸무게가 상한 바로 밑이면(I2) 그 줄을 고른다 — 상세 판정 카드도 같은 줄을 근거 목록(머리글 밑 점 줄)에 세워
  카드·지도 시트·상세가 같은 말을 한다. 상세에서 근거 목록 밖 작은 줄로 가는 info 는 요금(I1)뿐이다(전엔 `level !== 'info'` 로 갈라 I2 가 요금 줄에 ' · ' 로 붙었을 것).
  I2 줄은 무게 상한 칩('13kg 미만' · 구간 칩이면 그 줄이 말한 구간의 칩)과 같은 말이라 카드에선 그 칩이 빠진다(`REASON_BADGE`, H2 처럼 `saysNearLimitBound` 로 구간을 찾는다 — 경계 말('7kg 이하')까지만 맞춘다. 뒤 조사가 남은 무게로 '까지'·'에' 로 갈리기 때문이다).
  크기 언급 없음(I3)은 카드 이유 줄이 아니다 — 크기를 말하지 않은 곳이 많아(122곳 중 12kg 기준 51곳) 같은 줄이 수십 장에 붙는다. 상세 근거 목록에만 선다.
  목록 머리의 "N곳은 같은 이유예요"(`placesPageRepeatedReason`)는 I2 를 세지 않는다 — '갈 수 있어요' 카드의 참고 줄을 막힌 이유로 묶어 말하게 된다.
  보통은 최종 레벨과 같은 레벨의 첫 근거지만 cond 는 갈린다: 머리글이 "확인이 필요해요" 면 야외 자리 규칙(C1·C4·H4)이 **아닌** 근거다 — 무히어는
  '야외 자리만 가능해요' 가 앞에 서서 판정을 정한 예방접종이 상세에서야 보였다. 머리글이 "야외 자리에서 갈 수 있어요" 면 그 말을 되풀이하는 C1 은 고르지 않는다
  (카드 한 장에 '야외' 가 세 번이었다) — H4·C4 는 왜 야외만인지 더 말해 남는다(14 W261013.1).
  - **카드의 원문 칩은 판정과 같은 말을 한 번만 한다**(`verdictHidesBadge`, 목록 카드·지도 시트·상세의 근처 장소 카드 — 상세 원문 칩은 거르지 않는다). 칩은 원문 속성이고 판정은 우리 강아지의 답인데,
    나란히 서면 한 문장처럼 읽힌다. 받아 준다는 ✓ 칩(크기·실내)은 판정이 받아 줄 때만 선다 — '이용하기 어려워요' 옆 '✓ 중형견 OK'(웨스티하우스, 20kg 미만은 1마리),
    '확인이 필요해요' 옆 '✓ 실내 OK'(정체불명)가 판정과 반대로 읽혔다. 요금 ✓ 는 받아 주는지와 무관해 남지만, **어려움이면 요금 칩을 전부 뺀다** — 판정이 요금을 싣지 않는 것과 같은 이유다: '이용하기 어려워요' 옆 '1마리당 1~2만원'(웨스티하우스 × 콩·해피)은 우리가 낼 돈으로 읽혔다(14 W261013.1a). 머리글이 야외 자리를 말하면 '야외만' 을, 이유 줄이 말한 칸
    (전화 확인 · 예방접종 · 요일 · 무게 · 마릿수 · '케이지 필요' …)의 칩을 뺀다 — 짝은 규칙 ID → 그 칸의 배지 라벨이고, 라벨은 `toPetBadges` 와 같은 상수·함수(`BADGE_LABEL` …)라
    한쪽만 바뀌지 않는다. **줄을 목록 머리로 올린 카드는 칩을 남긴다**(그 카드의 유일한 단서다). 뺀 칩은 `+N` 에 세지 않는다. 판정과 `toPetBadges` 출력은 그대로다.
  - **이유 줄이 없는 카드(상세의 근처 장소, 칩 한 자리)는 판정을 정한 칩을 맨 앞에 세운다**(`reasonBadgeLabel` → `PetBadges` 의 `lead`, 14 W261013.1c). 판정 옆 한 자리는 이유로 읽힌다 —
    웨스티하우스 × 콩·해피가 판정을 정하지 않은 가장 낮은 구간 '10kg 미만 2마리' 를 세워 "2마리 된다는데 왜 어렵지" 였다(판정은 '20kg 미만 1마리'). 짝은 거르기와 같은 표(`REASON_BADGE`)라
    어려움만이 아니라 확인 필요(무히어 → '예방접종 필수')도 같다. 거르기와 방향이 반대라(줄이 있으면 빼고, 없으면 앞세운다) 입력을 나눈다 — 근처 카드는 `shownReason` 없이 거르므로 그 칩이 남는다. 순서만 바뀌어 `+N` 은 그대로다.
  - **목록의 과반이 같은 문장이면 머리로 올린다**(3곳 이상 + 과반, `placesPageRepeatedReason`). 식당 34곳 중 29곳이 "케이지라고 적혀 있어요. 이동가방도 되는지 확인해 주세요" 를 한 줄씩 되풀이해, 목록이 걸러 주는 게 없어 보였다(6/6, 14 W261006.5). 머리가 "29곳은 같은 이유예요" 로 한 번 말하고, 그 문장과 **같은** 카드만 줄을 뺀다 — 야외만·전화 확인처럼 다른 카드는 그대로라 다른 것만 눈에 띈다. 칩은 새로 만들지 않았다: 식당(케이지)에서는 남는 판정 배지("확인이 필요해요")와 원문 배지("케이지 필요")가 그 칩이다. 받칠 원문 배지가 없는 문장(카페 × 대형견의 "대형견 언급이 없어요")은 머리 상자의 곳 수 + 문장이 대신한다. 키는 규칙 ID 가 아니라 **문장**이다(같은 H1 이라도 kg 숫자가 다르다).
  - **갈 수 있는 곳이 0곳이면 야외 차선**을 같은 머리에 한 줄 — 카드 머리글이 "야외 자리에서 갈 수 있어요" 인 곳들(`outdoorFallback` 이 `isOutdoorSeatOnly` 로 고른다 — 수가 아니라 곳을 돌려준다). 크기·전화 확인이 남은 야외 곳까지 넣으면 "돼요" 한 줄 밑 시트의 카드가 "확인이 필요해요" 라고 했다. 줄은 문장 없이 「야외 자리 N곳 보기」 버튼 하나다 — 수는 머리 줄의 "야외 N" 이 이미 말한다("어려움 N곳 보기" 와 같은 이유, W261007.5a). 누르면 그 곳들만 시트로 펼쳐 바로 상세로 잇는다 — 기본 정렬은 그곳을 맨 앞에 두지만 가까운 순·가격 순에서는 흩어져 34곳을 훑게 된다. 실내 자리가 꼭 필요하면(`needsIndoor`) 말하지 않는다. 지금은 식당 × 대형견에서만 열린다(무거버거 1곳).
- 홈·목록 머리: 레벨별 곳 수를 **같은 함수**(`src/lib/eligibilityCounts.ts` 의 `countByLevel`)로 — 홈 "가능 3 · 확인 3", 목록 "26곳 · 가능 4 · 확인 4 · 정보 없음 4 · 어려움 14"(→ [features/home-header.md](../features/home-header.md)) 머리글이 "야외 자리에서 갈 수 있어요" 인 곳(`isOutdoorSeatOnly`)은 `cond` 가 아니라 **`outdoor` 칸**에 센다 — 같은 술어라 야외 차선(`outdoorFallback`)의 곳 수와 같다. 세는 칸이지 판정 레벨이 아니다.
- **이동 수단 what-if**(식당 탭, 프로필이 `none` 일 때): 지금 결과 중 어려움인 곳을 `carrier: 'bag'` 으로 다시 판정해 어려움에서 벗어나는 곳을 **새 판정 칸별로**(`countByLevel` 과 같은 가름 — 가능·야외·확인 필요) 세어 "어려움 35곳 중 이동가방이 있으면 2곳은 ‘가능’, 33곳은 ‘확인 필요’ 로 바뀌어요. 케이지라고 적힌 곳이 가방도 받는지는 물어봐야 알아요 · 우리 강아지 정보 고치기" 로 알린다(`carrierWhatIf` → `carrierWhatIfText`, `src/screens/placesPageResults.tsx`). 칸 이름이 바로 위 목록 머리와 같은 `LEVEL_COUNT_LABEL` 이라 가방으로 바꾼 뒤 머리 숫자가 어디로 옮겨 가는지 같은 말로 읽힌다. 원문이 '케이지' 라고 쓴 곳만 가방이면 확인(C2)이고, 이동가방을 적은 곳은 가방이면 가능이다 — 수 하나로 '확인 필요' 라고 하면 그 곳들을 틀리게 센다(14 W261013.14h). 머리 상자의 "N곳은 같은 이유예요" 와 이 줄의 수는 같은 무리가 아니다(같은 이유는 '케이지' 문장 곳만, what-if 는 어려움에서 벗어나는 곳 전부 — 광복이네는 이동가방 원문이지만 전화 확인이 남아 '확인 필요'). 그런데 읽는 사람에겐 같은 무리라 "32곳" 밑의 합 35 가 틀린 수로 읽혔다(평가 2/6, 14 W261019.3) — 수를 억지로 맞추지 않고 **무리의 이름**을 붙인다: 앞의 "어려움 N곳 중" 은 목록 머리 "어려움 N" 과 같은 수(`carrierWhatIf` 의 `hard`, 실데이터 테스트가 `countByLevel` 과 묶는다). 뒤 문장은 이유가 '케이지' 인데 고칠 것이 '이동가방' 인 까닭이고 C2 가 확인을 권하는 이유와 같은 말이라, 가방이면 C2 가 되는 곳 중 원문이 '케이지' 인 곳이 있을 때만 붙는다(`cageAsk` — 유모차만 적은 곳의 C2 는 "유모차라고 적혀 있어요" 라 '케이지' 라고 부르면 다른 조건이 된다). 같은 이유 문장·야외 차선과 **한 상자**에 모인다 — 케이지 이유와 그 출구가 따로 쌓이면 같은 이야기를 두 번 한다. **what-if 는 판정을 바꾸지 않고 안내만 한다** — 등급·배지("케이지 필요")·준비물 표(`ITEM_NEEDS`, ADR-009)는 그대로고, 바꾸는 길은 프로필(`/dog`) 하나다. 대형견은 가방이어도 H4 가 그대로라 0 → 줄을 그리지 않는다.
- 지도: 마커 색과 시트 라벨이 판정 레벨을 따른다(`src/screens/mapPage.tsx`, `mapPageSheet.tsx`). 마커의 접근성 이름은 목록 배지와 같은 `headlineFor` 문장이다(`mapPageCanvasMarkerLabel` — 레벨 이름을 붙이던 동안 야외 자리 곳을 '확인이 필요해요' 로 읽었다, 14 W261013.3).
- 프로필이 없으면 필터만 있는 화면으로 폴백하고, 홈에 "우리 강아지 등록하기" 진입(`/dog`).

### 다두 what-if — `src/lib/dogSubsetWhatIf.ts`

여러 마리인데 **어려움**이면, 마리 부분집합(3마리면 6개)마다 `judgeEligibility` 를 다시 돌려 갈 수 있는 조합 하나를 상세 판정 카드에 한 줄로 말한다 —
"초코만 데려가면 갈 수 있어요"(10 F11, 태호). 규칙을 새로 쓰지 않으니 무게·마릿수·요금 규칙이 바뀌어도 따라간다.

- **어려움일 때만.** 확인 필요(cond)에서 "한 마리만 가면 확인 없이" 는 판정을 뒤집는 말이 아니라 소음이다. 정보 없음(unknown)이 나오는 조합은 고르지 않는다.
- **가장 많이 데려가는 조합**(두고 갈 아이가 적은 쪽) → 판정이 나은 쪽 → 무거운 쪽.
- **수도 판정도 같은 조합이 여럿이면 누구로도 된다고 말한다**(`ties` · `dogSubsetLead`, 14 W261019.9) — "콩이나 해피 중 한 마리만 데려가면" ·
  3마리에서 누구 한 마리만 빼도 되면 "단비, 솜이, 구름이 중 한 마리만 두고 가면". 웨스티하우스(10kg 미만 2마리 · 20kg 미만 1마리)에 콩 2.5kg·해피 12kg 는
  누구 한 마리만 가도 되는데 무거운 쪽 규칙이 "해피만 데려가면" 을 골라 "콩은 안 되는 줄 알았다" 였다. 판정이 다른 조합은 묶지 않는다 —
  뒤에 붙는 머리글("갈 수 있어요")이 모두에게 참이어야 해서다(콩 ok · 해피 확인 필요면 "콩이만"). 일정의 하루 줄도 같은 `dogSubsetLead` 로
  "이 날은 콩이나 해피 중 한 마리만 데려가면 다 갈 수 있어요" 라 한다(14 W261019.9a) — 묶음은 하루 전체로 세므로 다른 곳이 해피를 막으면 "콩이만" 이다.
- **크기 수정(`sizeOverride`)은 가져가지 않는다** — 가장 큰 아이를 고친 값이라, 작은 아이만 남으면 틀린 크기가 된다. 이동 수단은 그대로(보호자 것).

## 4. AI 구조화 판단 — `withPolicyFacts` (블로그 경로, ADR-017)

블로그에서 온 장소는 `TPlace.petPolicy`(`TPetPolicyFacts`, DB `places.pet_policy`)에 AI 가 원문을 읽고 판단한 값이 있다 — 실내 정책 · 리드줄 · 대형견 · 소형견만 ·
전화 확인 · 추가 요금(`fees`) · 무게 상한 · 마릿수 · 비고. 조립 `derivePlace`(`src/lib/placeDerive.ts`)가 `withPolicyFacts(parsePetPolicy(text), petPolicy, text)` 를 부르고(원문 공개 행·`/admin` 은 런타임에, 블로그 출처 행은 빌드 `pull-db` 에서 — 21 S8),
**facts 가 있으면 판정 필드를 그 값만으로 정한다**(v17, ADR-017 v5). `unknown`/`null` 은 "모름" 이 아니라 "읽어 봤는데 그런 조건이 없다" 다 —
스키마가 모든 칸을 요구하므로. 정규식 결과는 근거 문장(`sources`, AI 와 같은 판단을 짚었을 때만)과 AI 에 칸이 없는 허용 단서
(`outdoorFree`·`unlimitedDogs`)에만 남는다. 정규식이 같은 판단을 못 짚었으면 근거는 **그 판단의 근거 단어가 든 줄**이다 — 단어는 보정(`correctPetPolicyFacts`)이
판단을 남길 때 대 보는 것과 같은 표(`INDOOR_GROUNDS`·`VACCINE_GROUNDS`)라, 남은 판단에는 늘 그 말이 든 줄이 있다. 실내만 이 단어가 빠져 첫 줄("애견동반 가능 카페.")이
케이지 근거로 서던 것을 v52 에서 메웠다 — 인용·`/admin` 칠하기·가방 판독(`indoorGearText`)이 모두 이 줄을 쓴다. 무게·마릿수는 한 칸짜리 `tiers` 로 넣어 H1·H2 가 같은 숫자를 본다. AI 는 숫자만 주므로 경계(`weightInclusive`)는 원문에서 읽는다 — 그 숫자 뒤에 "미만" 이 있으면 제외, 아니면 포함(정규식 tier 와 같은 기본). 늘 포함으로 두면 "7kg 미만" 인 곳에 7kg 강아지가 '갈 수 있어요' 가 된다.

**왜 정규식으로 메우지 않나** — 정규식은 무게 상한과 요금 구간을 가르지 못한다. 다와풀빌라 `19kg 이하 1마리당 20,000원` 에서 AI 는 상한 없음(null)으로 맞게 읽었는데,
v16 까지는 null 을 "언급 없음" 으로 보고 정규식의 `~19kg` 을 남겨 25kg 강아지를 H1 **어려움**으로 보냈다. 어긋남은 검수의 `AI≠정규식` 표식이 보여 준다.

요금은 두 갈래다. **구조(`fees`)가 있으면** 그 label 이 `feeLines` 가 되고 `feeRules` 로 실려 `formatDogFee` 가 칸으로 계산한다(§3 요금). **구조가 없는 옛 판단**은
v14 의 잔여 병합 그대로다 — AI 목록을 앞에 세우고 파서 줄은 **금액(원 단위)이 전부 덮인 것만** 버린다. 옛 후보는 요금이 한 칸(`feeText`)이라, 통째로 믿으면
원문 `1마리당 3만원. (2마리 또는 10kg 이상 4만원)` 의 둘째 줄이 사라져 2마리를 "6만원" 으로 곱한다(원문은 4만원). 금액을 숫자 조각이 아니라 원 단위로 대 보는 것은
`2만원`(정규화된 AI 줄)과 `20,000원`(원문 줄)을 같은 요금으로 보기 위해서다 — 전에는 같은 요금이 두 번 섰다.
시드 86곳은 `petPolicy` 가 없어 이 함수를 그대로 통과한다 — 정규식이 시드의 유일한 경로다(AI 판단 채우기는 보류, ADR-017 결정 10).
왜 정규식만으로 안 됐나 — 첫 `pnpm data analyze`(2026-09-28)의 조건 문장 32건 중 20건을 어떤 규칙도 못 읽었다. 구어체는 끝이 없어 판단을 모델에 맡기고,
사람 검수(`pnpm data:review`)가 `정규식 [..] · AI [..] · 앱 [..]` 을 나란히 보며 어긋남을 잡는다.

### 덮기 전의 보정 — AI 판단도 원문에 대 본다 (v13)

모델은 원문에 없는 것을 낸다 — "애견동반 가능해요!" 에 `weightLimitKg: 10` 을 붙이면 그 숫자가 대형견을 H1 로 **어려움**에 보낸다.
틀린 제한은 틀린 허용만큼 해롭다(갈 수 있는 곳을 지운다). 그래서 `withPolicyFacts` 는 쓰기 전에 원문에 대 본다.

1. **`correctPetPolicyFacts(facts, text)`**(`scripts/lib/petPolicyFacts.mjs`) — 판단마다 원문에 근거가 있어야 남는다.
   숫자는 그 숫자가 원문에 `N kg`·`N마리`(한글 수사 포함)로 있어야 하고, 참/거짓은 근거 단어(대형·소형·리드·전화·야외…)가 있어야 한다.
   "대형" 이란 말 없이 무게 상한에서 추론한 `largeDogOk: false` 도 뺀다 — 그 제한은 무게 상한이 이미 H1 로 말한다.
   한 판단 안의 모순(소형견만 + 대형견 가능 · 금액 있는 요금 문장 + 추가 요금 없음)은 **허용 쪽**을 뺀다.
   **같은 함수가 두 곳에서 돈다** — 분석 시점(`extractPlaces.normalizePetPolicy`, 저장 전)과 앱(`withPolicyFacts` — 공개 행은 읽을 때, 블로그 출처 행은 빌드 때. 규칙을 고치면 `pnpm data pull --offline` 으로 다시 계산한다). 앱에서도 부르는 이유는
   보정 전에 분석된 후보(2026-09-28 첫 실행 160건)가 DB 에 그대로 있어서다. 두 번 불러도 결과가 같다(테스트가 잡는다).
   **요금은 줄마다 따로, 금액 토큰째로** 대 본다(v14). 숫자 조각만 보면 줄이 짧아진 만큼 검사가 약해진다 —
   `청소비 5만원` 의 `5` 는 원문 `1박 15만원부터` 안에도 있다. 금액(`5만원`)을 찾고 앞에 숫자가 붙지 않은 자리만 인정한다. 한 덩어리로 보면 근거 있는 줄 하나가 지어낸 줄들을 통과시키고, 반대로 지어낸 줄 하나가 옳은 구간표를 통째로 지운다.
   '금액 있는 요금 + 추가 요금 없음' 모순도 **어느 줄에서든** 금액을 보면 성립한다 — 첫 줄만 보면 "첫 마리 무료, 둘째부터 2만원" 을 놓친다.
   옛 후보·장소는 `feeText` 하나만 들고 있어 읽는 쪽이 `feeLinesOf` 로 둘을 합쳐 본다(소급 마이그레이션 없음).
   **요금 구조는 줄과 계산 칸을 따로** 본다(v17). 줄이 원문에 없으면 뺀다. 줄은 있는데 금액·몸무게 경계·몇째 마리가 원문과 안 맞으면 **계산에서만** 뺀다(`amountWon: null`).
   계산 칸의 근거는 상한·마릿수 판단보다 넓다(v46) — 구간 하한(`1~5kg` 의 1) · `N마리를 초과`(= N+1째부터) · `N마리가 포함`(= 기본 N마리, v48) · `첫 1박`(1박마다가 아니다) · 섞은 금액(`1만5천원` = 15000)을
   읽지 못해 모델이 맞게 낸 요금을 지웠다([BUG-018](../bugs/BUG-018-fee-grounding-drops-correct-amounts.md)). 구간 하한·초과는 **요금 칸에서만** 근거다 — `weightLimitKg`·`maxDogs` 가 받으면 없는 제한이 생긴다.
   반대로 칸이 표현 못 하는 조건은 근거가 있어도 계산하지 않는다 — `2박째부터 1박당 1만원` 은 몇째 밤부터인지 자리가 없어(`perNight` 하나) 계산하면 1박 손님에게도 1만원이다(v47).
2. ~~**제한은 정규식이 이긴다**~~ — v17 에서 거뒀다(ADR-017 v5 결정 7). 정규식이 읽은 '제한' 이 선택지(`리드줄이나 케이지`)·권유(`켄넬을 챙겨가면 더 쾌적`)·
   요금 기준(`19kg 이하 …원`)에서 왔고, 대조한 세 건 모두 AI 가 맞았다. 근거 없이 지어낸 허용은 1번이 막는다.

검수 화면은 뺀 것을 숨기지 않는다 — `previewPolicy` 가 `corrections` 를 싣고 표식 `AI 판단 보정`(`/admin` 에선 `AI 판단 일부 뺌`)을 붙이며,
펼친 상세에 "원문에 없어 뺀 것: …" 줄이 뜬다. `facts` 자체는 모델이 낸 그대로 둔다 — 무엇을 잘못 읽었는지가 프롬프트를 고칠 재료라서다.
